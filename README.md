# OTA Platform

自托管的 Expo 热更新服务端，带口令激活、代理分销和管理后台。

服务端兼容 Expo Updates 协议 v0 / v1，App 接入只需修改 `app.json`，不用改代码。整个服务是一个 jar：内置 H2 数据库，也可以接 MySQL；更新包文件存在本机磁盘或任意 S3 兼容对象存储，App 可以直接从 CDN 下载。

## 功能概览

- 热更新：多 App、多渠道，按 Runtime 管理版本；支持灰度发布、回滚到任意旧版本、回退到安装包内置版本，以及定时调整灰度。
- 口令更新：同一个检查更新地址，新装 App 输入口令激活时可以下载单独指定的更新包，已激活的设备照常拿常规更新。
- 增量更新：发布后为最近几个版本生成启动包的 bsdiff 补丁，设备只下载差异。
- 代码签名：每个 App 使用独立的 RSA 签名密钥，也可以复用其他 App 的密钥。
- 发布监控：统计每个版本的推送、下载、装上和启动失败，并归类启动崩溃。数据来自 expo-updates 自带的请求头，App 不用加代码。失败率超过阈值时告警，也可以设置自动回滚。
- 排查工具：测试设备、灰度白名单、推到其他渠道、模拟检查更新；上传 APK / IPA 后逐项检查与服务器配置是否一致。
- 口令与激活：口令所有 App 通用，HMAC 签名的兑换接口带防重放；A / B 面切换、使用上限、有效期、绑定渠道；按设备指纹跨 App 去重，统计日活与留存。
- 代理：代理后台、二级代理、口令申请与审核、按日扣量与结算、公告。
- 后台：超级管理员和成员两种角色，成员按 App 授权；支持两步验证；后台包括可自定义的概览看板、数据大屏、免登录的大屏分享链接和全局搜索；提供中英文界面，适配手机。
- 运维：网页安装引导、加密备份与恢复、存储在线切换、健康检查、Prometheus 指标、操作日志。

## 快速开始

### 环境要求

运行需要 Java 17。从源码打包另外需要 Maven 和 Node.js 18 以上。

### 打包与运行

```bash
./build.sh                         # 先打包前端，再打包后端，输出 target/ota-platform.jar
java -jar target/ota-platform.jar
```

导出的项目压缩包里带有打好的 `dist/ota-platform.jar`，可以直接运行。服务默认监听 8812 端口：

| 路径 | 内容 |
| --- | --- |
| `/` | 产品介绍页（静态页面，中英文） |
| `/login` | 管理员和代理共用的登录页 |
| `/admin` | 管理后台 |
| `/agent` | 代理后台 |

### 安装引导

第一次用浏览器打开 `http://服务器地址:8812`，按引导完成四步设置：

1. 数据库：选 MySQL 5.7 / 8.0（先建好 utf8mb4 的空库）或内置 H2。正式环境建议用 MySQL。库里已有数据时可以选择保留或清空，清空需要再输入「清空」确认。
2. 访问域名：可以绑定多个域名，每个域名勾选用于后台、接口或两者，域名可以带端口。开启「只允许这些域名访问」后，其他域名一律返回 404；`127.0.0.1` 和 `localhost` 始终可以访问。
3. 文件存储与高级设置：本机存储或 S3 兼容存储、后台显示时区、旧安装包兼容入口。
4. 超级管理员账号。

提交后服务在进程内自动重启，大约十几秒。配置保存在 `data/install.json`，其中的密码和密钥用主密钥加密。安装完成后：

- 在「系统配置 → 安装与域名」修改访问域名和对外地址，修改立即生效。
- 在「系统配置 → 存储」切换文件存储。
- 验证登录密码后可以重新进入安装引导，例如更换数据库。

接口对外地址用于 App 下载文件，也显示在 API 文档和接入配置里，默认取第一个接口域名。反向代理一般会去掉 Host 里的端口，所以引导页按浏览器地址栏预填域名。对外地址和某个接口域名是同一主机但缺少端口时，保存时会自动补上。

脚本或容器部署可以跳过引导页：启动时设置环境变量 `OTA_ADMIN_PASSWORD`，服务直接视为已安装，管理员账号为 `admin`；`OTA_BOOTSTRAP_TOKEN` 用来指定初始管理令牌。启动参数和环境变量的优先级高于 `install.json`。

### 数据目录

数据默认放在 `./data`，可以用 `--ota.data-dir` 修改：

| 路径 | 内容 |
| --- | --- |
| `db/` | 内置 H2 数据库 |
| `blobs/` | 本机存储的版本文件、补丁和安装包 |
| `master.key` | 主密钥，用来加密签名私钥、两步验证密钥和 `install.json` 里的密码。丢失后这些数据无法解密，务必备份；生产环境建议改用环境变量 `OTA_MASTER_KEY` |
| `install.json` | 安装引导保存的配置，只有运行服务的账号能读写 |
| `backups/` | 每日自动备份（不加密） |
| `restore/` | 恢复备份前原数据的副本 |
| `demo/` | 演示环境的独立数据 |

### Docker

```bash
docker compose -f deploy/docker/docker-compose.yml up -d
```

启动前修改 `deploy/docker/docker-compose.yml` 里的 `OTA_PUBLICURL`；使用 MySQL 时取消文件里对应的注释。数据挂载在项目根目录的 `data`。只构建镜像：`docker build -f deploy/docker/Dockerfile -t ota-platform .`。

## 接入 App

1. 在后台「所有 App」新建 App。名称填用户手机上看到的名字，可以顺便填应用商店或官网的下载链接。新 App 会自动生成签名密钥；如果 App 已经发布、安装包里内置了证书，就导入当时的密钥对。
2. 在「App 设置」下载证书，放到 App 项目的 `certs/certificate.pem`。
3. 修改 `app.json`，然后重新打包安装包：

```json
{
  "expo": {
    "runtimeVersion": { "policy": "appVersion" },
    "updates": {
      "url": "https://ota.example.com/m/my-app",
      "requestHeaders": { "expo-channel-name": "production" },
      "codeSigningCertificate": "./certs/certificate.pem",
      "codeSigningMetadata": { "keyid": "main", "alg": "rsa-v1_5-sha256" }
    }
  }
}
```

`url` 末尾的 `my-app` 是 App 标识，渠道由请求头 `expo-channel-name` 指定。「签名配置」页的「在 App 里使用」一栏汇总了证书下载、keyid、算法和可以直接复制的 `app.json` 配置。

## 发布更新

### 命令行

`cli/` 下是命令行工具 `ota`，只依赖 Node.js：

```bash
cd cli && npm link                 # 或者直接运行 node cli/bin/ota.mjs
ota login --server https://ota.example.com --token ota_xxx
cd 你的 App 目录
ota publish --app my-app --message "修复登录页"            # 导出、只上传有变化的文件、发布到 production
ota publish --app my-app --channel staging --rollout 20    # 指定渠道和灰度比例
ota publish --app my-app --as activation                   # 发布成口令更新
ota rollback --app my-app --runtime 1.0.0                  # 回滚到上一版本
ota rollback --app my-app --runtime 1.0.0 --to 4a55bc34    # 回滚到指定版本（版本 ID 前 8 位即可）
```

| 命令 | 作用 |
| --- | --- |
| `login` | 保存服务地址和令牌到 `~/.ota/config.json` |
| `apps` | 列出能访问的 App |
| `publish` | 导出并发布。不带 `--dir` 时在当前目录运行 `npx expo export`；`--no-deploy` 只登记不发布 |
| `releases` | 最近的版本、各渠道的线上版本和口令更新包 |
| `deploy` | 发布已登记的版本，或调整灰度比例 |
| `activation clear` | 取消口令更新包，激活时改回下载常规更新包 |
| `rollback` | 回滚；`--to` 指定版本，`--embedded` 回退到安装包内置版本 |
| `verify` | 校验版本的文件、哈希、Runtime 和签名 |
| `stats` | 近 30 天设备的版本分布 |
| `cert` | 下载 App 内置用的证书 |
| `installer upload` / `list` | 上传 APK / IPA（自动分片）并显示检查结果，有不通过的项时退出码为 2；列出已上传的安装包 |
| `schedule list` / `rollout` / `mode` / `cancel` | 查看、新建、取消计划任务 |

`--server`、`--token` 可以覆盖已保存的配置，也可以用环境变量 `OTA_SERVER`、`OTA_TOKEN` 传入；`--json` 输出 JSON。运行 `ota help` 查看全部参数。

### 令牌

| 令牌 | 在哪里创建 | 权限范围 |
| --- | --- | --- |
| 发布令牌 | App 设置 → 发布令牌 | 只能操作一个 App，适合放在 CI 里 |
| 管理令牌 | 系统配置 → 管理令牌 | 所有 App；定时切换 A / B 面等操作必须用它 |
| 监控令牌 | 系统配置 → 运行信息 → 监控指标 | 只能读取 `/api/metrics` |

令牌的明文只在创建时显示一次，之后列表里只显示开头几位。管理接口的完整说明见后台「API 文档」，「系统配置 → 管理令牌」里有用当前服务地址写好的命令行和 curl 示例。

### 在后台发布

在「版本发布」页上传 `expo export` 生成的 ZIP，或者添加放在 CDN 上的 dist 目录地址（外部链接版本）。上传时可以直接选择发布到哪个渠道，以及作为常规更新还是口令更新。

## 版本管理

### 基本概念

- Runtime：同一个 Runtime 的版本才能互相替换，由 `app.json` 的 `runtimeVersion` 决定。
- 渠道：一个 App 可以有多个渠道（如 production、beta），每个渠道的每个 Runtime 各有一个线上版本。
- 版本：一次发布的完整更新包。文件按 SHA-256 存储，相同内容只存一份、只上传一次，删除版本时不会立即删除文件。

每次发布、调整灰度、回滚、回退内置版本都记入发布记录。「版本发布」页显示最近 10 条，更早的记录用 `GET /api/v1/apps/{app}/history?limit=200` 查询。

### 灰度

灰度按设备 ID 固定分组，组外的设备继续使用上一版本。

还在运行安装包内置版本的设备（新安装、正在输入口令激活的）不在灰度组内时，同样拿到上一版本；如果没有上一版本（第一次发布就设了灰度，或者上一版本已删除），则直接拿到线上版本。这样输入口令后总能下载到一个版本、完成激活。已经装过热更新又不在灰度组内的设备不会更新。

### 回滚与回退内置版本

「回滚」列出同一 Runtime 之前的所有版本，默认选中上一版本。

- 回滚到比线上旧的版本时，服务器把它复制成一个内容相同的新版本再发布，已经更新过的设备下次检查更新时也会换回去。
- 如果要发布的版本和线上内容相同（一个是另一个的副本），就不复制，只调整灰度。发布弹窗会提前写明这次是否复制。

回退到安装包内置版本后，设备会退回安装包里的版本，之后可以用「回滚」选一个版本恢复。渠道某个 Runtime 已经没有更新包时，线上版本列表不再显示这一行，但回退内置版本的指令仍会下发给尚未联网的设备。

### 删除版本

以下版本不能删除，版本的操作菜单里会写明原因：

- 渠道的线上版本；
- 口令更新包；
- 灰度未到 100% 时其余设备拿的上一版本。

只用于回滚的上一版本可以删除，之后回滚时另选版本。删除版本不删除文件，没有版本使用的文件在「系统配置 → 存储 → 清理无用文件」中清理。

### 常规更新与口令更新

每个渠道的每个 Runtime 可以设置两种包，检查更新使用同一个地址：

- 常规更新：即线上版本。已激活的设备检查更新时下载它，支持灰度和回滚。
- 口令更新：单独指定的一个包。新装 App 输入口令激活时（设备还在运行内置版本）下载它，不参与灰度，也不受回退内置版本的影响。口令更新包缺少某个平台的文件时，该平台设备仍然下载常规更新包。

服务器按设备当前运行的版本区分两种情况：请求头 `expo-current-update-id` 等于 `expo-embedded-update-id`（或者没有这个头）时，视为设备还在运行内置版本。没有单独设置口令更新包时，激活时下载的就是常规更新包。

设置口令更新包的方式：

- 「版本发布」页每个线上版本下方的「口令更新」一行，可以设置、更换、取消；
- 发布弹窗中选择「口令更新」，或者上传版本时选择「作为口令更新」；
- 命令行 `ota publish --as activation`、`ota deploy --release <ID> --as activation`，取消用 `ota activation clear`；
- 管理接口发布时传 `"as": "activation"`，取消用 `POST /api/v1/apps/{app}/channels/{channel}/activation/clear`。不传这个参数时行为与普通发布相同。

expo-updates 只安装比当前运行版本更新的更新包，所以口令更新包必须晚于安装包的打包时间。重新打包安装包后，要换成之后上传的版本，否则新装用户收不到口令更新包；上传安装包后的检查会提示这个问题。设备激活后已经在运行口令更新包，下次检查更新就按常规更新处理。

### 增量更新

发布后服务器为最近 3 个版本（`ota.patch.bases`）生成启动包的 bsdiff 补丁，补丁大于完整文件的 80%（`ota.patch.max-ratio`）时不使用。设备只下载补丁，补丁应用失败时 expo-updates 自动改为下载完整文件。每个 App 可以在 App 设置中单独关闭。

### 计划任务

- 定时切换 A / B 面：在概览「运行模式」卡片中设置，例如审核通过后约定时间上线。
- 定时调整灰度：在「版本发布」页每个渠道的灰度旁边设置。到时间时如果该渠道的线上版本已经换了，计划不执行，避免把新版本直接放量。

计划最多提前 90 天，按后台时区执行，服务每 30 秒检查一次，执行结果记入操作日志（操作人为「计划任务」）并发送通知。定时切换需要「切换 A/B 面」权限，定时调整灰度需要「发布版本」权限。也可以通过 `/api/v1/apps/{app}/schedules` 或 `ota schedule` 设置：定时调整灰度可以用发布令牌，定时切换必须用管理令牌。

### 测试与排查

- 测试设备：在「设备统计」中把一台设备设为测试设备，指定它使用 beta 等渠道，不用重新打包。勾选「灰度白名单」后，渠道灰度未到 100% 时这台设备也先拿线上版本。管理接口添加测试设备时传 `rolloutFirst: true` 效果相同。
- 推到其他渠道：在测试渠道验证好的版本，原样发布到 production。
- 诊断与模拟检查更新：按设备的真实条件走一遍服务器的判断，说明它会拿到哪个版本（常规更新还是口令更新）、按的是哪条规则。

## 发布监控

expo-updates 检查更新时会带上设备当前版本、最近启动失败的版本（`Expo-Recent-Failed-Update-IDs`）和上次崩溃的错误（`Expo-Fatal-Error`），下载文件时会带上正在下载的版本。服务器据此统计每个版本的数据：

| 指标 | 含义 |
| --- | --- |
| 推送 | 检查更新时下发了这个版本的设备数 |
| 下载 | 下载了这个版本文件的设备数 |
| 装上 | 重启后运行这个版本的设备数 |
| 启动失败 | 启动这个版本失败、自动退回之前版本的设备数 |
| 流量 | 启动包按补丁和完整文件下载的次数，补丁节省的字节数 |

启动错误按设备和错误去重，6 小时内只记一次，保留 30 天。版本详情中按错误第一行归类（去掉堆栈），列出最常见的几类及其占比、iOS / Android 次数和最近一次的时间。

### 告警与自动回滚

线上版本启动失败至少 3 台、且失败率不低于 5% 时，版本页、概览和所有 App 页面都会提示，同时发送 Webhook `release.launch_failures` 和群机器人消息。

自动回滚默认关闭，每个 App 单独设置。在「版本发布」页线上版本标题旁边开启，选择失败率阈值（5% / 10% / 20% / 30%）和最少失败设备数（3 / 5 / 10 / 20 / 50）。达到阈值后自动回滚到上一版本，过程与手动回滚相同，操作人记为「自动回滚」。每个版本只自动回滚一次；渠道没有上一版本，或者上一版本本身就是被自动回滚掉的，则只告警不回滚。

### 通知

群机器人在「App 设置 → 通知」中配置，支持钉钉、飞书、企业微信，按地址自动识别。发布、回滚、回退内置版本、切换 A / B 面和启动失败告警都会通知，也可以只勾选其中几类。

Webhook 事件：

| 事件 | 触发时机 |
| --- | --- |
| `release.deployed` | 发布版本或调整灰度 |
| `release.rolledback` | 回滚 |
| `release.embedded` | 回退到安装包内置版本 |
| `release.activation_deployed` | 设置口令更新包 |
| `release.activation_cleared` | 取消口令更新包 |
| `release.launch_failures` | 启动失败超过阈值 |
| `release.auto_rollback` | 自动回滚 |
| `mode.switched` | 切换 A / B 面 |

接收方应先用请求头 `X-OTA-Signature` 验签再处理，App 设置里提供了填好密钥的 Node.js 验签示例。「App 设置 → 通知」下方保存最近 30 次发送记录（时间、事件、结果、失败原因、重试次数），只记录对方域名，不保存地址中的令牌。

## 安装包校验与更新包结构

在「版本发布 → 安装包」上传 APK 或 IPA（最大 1 GB），也可以用 `ota installer upload` 或管理接口上传。文件按几 MB 一片分片上传，不受反向代理请求大小限制。服务器读出包名、版本号、Runtime、更新地址、渠道、内置证书和内置更新包，逐项检查：

- 更新地址是否指向本服务（对外地址或绑定的接口域名），是否为 HTTPS。iOS ATS 和 Android 默认会拦截明文 HTTP，除非安装包允许明文流量。
- 对应的 Runtime 和渠道（未指定时为 production）是否存在、是否有版本。
- 内置证书和 App 的签名证书是否同一把密钥，keyid 是否正确（安装包没写 keyid 时 expo-updates 按 `root` 处理），算法是否为 rsa-v1_5-sha256，更新功能是否被关闭。
- 渠道线上版本是否晚于安装包内置版本的打包时间（`app.manifest` 的 `commitTime`）。不晚的话 App 会认为没有新更新；渠道设置了口令更新包时，比对的是口令更新包。
- 启动时检查更新的设置（iOS `EXUpdatesCheckOnLaunch`、Android `EXPO_UPDATES_CHECK_ON_LAUNCH`）。值为 `ERROR_RECOVERY_ONLY` 或 `NEVER` 时，只能在 App 里调用 `fetchUpdateAsync` 获取更新。
- 安装包里是否有内置更新，回退内置版本依赖它。

检查结果显示在安装包列表中；版本的「校验」也会同时检查同 Runtime、同平台的安装包。

版本详情中的「更新包结构」列出每个平台的全部文件（外部链接版本也可以查看），包括大小和 SHA-256。可以选一个旧版本对比，标出新增、有变化、未变化的文件、从旧版本更新需要下载的大小，以及走增量补丁的启动包。

## 口令与激活

### A / B 面

每个 App 有两种运行模式：

- A 面：审核模式，口令不能兑换；
- B 面：上线模式，用户提交有效口令即可进入 B 面。

切换需要「切换 A/B 面」权限，也可以设置定时切换。

### 口令

- 口令所有 App 通用：一个口令可以在任意 App 中兑换，使用次数合并计算。
- 口令可以批量生成，也可以导入已有口令；可以设置使用上限、有效期，以及绑定渠道（兑换成功后 App 切换到该渠道）。
- 后台可以按状态、代理、关键字筛选口令，并批量启用、停用、分配和删除。
- 口令列表本身不提供导出；激活记录、设备列表、代理列表和单个代理的激活记录可以导出 CSV。

### 口令接口

App 通过三个接口完成激活，请求用 HMAC 签名并防重放：

| 接口 | 调用时机 |
| --- | --- |
| `POST /v1/codes/redeem` | 用户提交口令时兑换 |
| `POST /v1/codes/confirm` | B 面启动成功后确认激活 |
| `POST /v1/codes/verify` | App 每次启动时校验授权 |

请求头包括 `X-App-Key`、`X-Timestamp`、`X-Nonce` 和 `X-Signature`。「App 设置 → 口令接口」提供 App Key、签名密钥、请求格式，以及填好这个 App 的密钥和地址、可以直接复制的签名请求示例。

### 激活记录

激活记录可以按 App、代理、时间段和设备筛选，页面带对账汇总，导出的 CSV 即为对账明细。以下几类记录不算有效激活：

- 确认过快：兑换后不到 2 秒就来确认（真机需要先下载 B 面包、重启后才会确认），判为脚本刷量。这类记录不占口令次数，不计入代理数据和日活；App 端照常返回成功，不暴露判定规则。阈值由 `--ota.min-confirm-ms` 设置，设为 0 关闭。管理接口中对应 `status=fast`。
- 重复：同一台设备已经在别处计算过有效激活，见下一节。管理接口中对应 `status=dup`，`dupOf` 指向原记录，`dupBy` 说明识别方式。

代理后台把这两类记录显示为「无效用户」或「重复」，只显示判定结果，不显示依据。

### 跨 App 设备去重

同一个 App 内，一台设备再次兑换同一口令或换口令兑换，都沿用原来的激活。跨 App 去重由每个 App 的「App 设置 → 按设备去重」开关控制，默认关闭。

开启后，确认激活时计算设备指纹：

1. 首选 `/var/mobile` 的创建时间（毫秒）加机型。不同开发者账号的 App 读到的值相同，所以可以跨 App、跨账号识别同一台手机。
2. 读不到时，用公网 IP 加机型兜底。
3. 都没有时按设备号识别。

App 在 `/v1/codes/verify` 和 `/confirm` 请求中带上两个可选字段：`init`（`/var/mobile` 创建时间）和 `model`（机型），旧版本 App 不带也能正常工作。指纹补写、日活记录和最近活跃时间都在后台线程写入，不拖慢接口。

升级前就已激活的设备，会在下一次校验时补写指纹，因此新 App 上线前应尽早发布带指纹的 B 面包。指纹保留期在 App 设置中选择 7 / 30 / 90 天或一直保留，默认 7 天；设备超过保留期没有打开 App，就清除它的指纹。

> 读取 `/var/mobile` 创建时间做跨 App 设备识别，与国内广告行业的 CAID 方案相同，违反 App Store 审核条款，存在被拒审或下架的风险。该时间精确到毫秒，有极小概率两台设备相同；手机抹掉所有内容或整机恢复后指纹会变化。上线前请用真机验证能否读取。

### 日活与留存

App 启动时校验授权或确认激活，这台设备当天就计为活跃，每天只计一次，记在激活它的口令名下，数据不扣量。数据存放在 `activation_day` 表，保留 400 天，从升级到包含此功能的版本那天开始记录。

日活与留存页面只有管理员能看，可以查看全部代理、单个代理（含其二级代理）或单个口令。指标包括：

- 今日日活和今日新激活；
- 昨日日活及其环比；
- 活跃率；
- 次日留存和 7 日留存；
- 每日新激活设备在第 1 / 3 / 7 / 14 / 30 天的留存表。

代理后台另有「留存」页，只显示 7 日内的留存百分比，不显示台数。

## 代理

代理账号所有 App 共用，口令归属到代理。管理员在「代理管理」中为每个代理设置：

- 可见范围：能否查看设备级的激活记录，还是只看数量。
- 数据更新方式：实时、每日 0 点，或手动更新（代理只能看到上级最后一次点「更新」时为止的数据）。
- 口令申请方式：不能申请、需要审核或自动通过，以及每天最多申请多少个（待审核和已通过的都计入，自动通过也受限）。
- 扣量档位。
- 是否允许开设二级代理，以及数量上限。

可以勾选多个代理批量设置申请方式、启用、停用或删除。删除代理时可以选择只删账号（名下口令变为未分配），或者连同其口令、激活记录和申请一起删除，后者需要输入登录密码。

### 口令申请

代理可以选择随机生成（随机 8 位数字）或自定义口令（每行一个）。自定义口令与已有口令、正在审核的申请重复时，提交时直接拒绝并列出重复项。

管理员在「代理管理 → 口令申请」集中审核：随机申请可以修改个数、可用次数和有效期，自定义申请可以逐个勾选同意哪些；支持批量同意或拒绝，拒绝时可以填写原因。同意申请需要「口令与激活」权限。

### 扣量与结算

扣量按天计算：当天的有效激活数落在哪一档，就按该档比例扣除。扣除数量先按二级代理（一级代理自留的口令算一份）当天的激活数分摊，再分摊到每个口令，每个口令扣最晚确认的几条。修改档位只影响修改之后确认的激活。

扣量结果在结算时间写入 `agent_settlement` 表，每个代理每天一行，写入后不再改变：

- 实时和每日 0 点更新的代理，在每天 0 点结算前一天；服务停机错过时，启动后补结算。
- 手动更新的代理，在点「更新」时结算到当时为止。

从没有结算表的旧版本升级时，第一次启动会按旧算法把每个代理当时看到的数字写入结算表，已经展示过的数字不会变化。

设置了使用次数的口令，按代理看到的有效激活计算次数，被扣掉的激活不占次数。这样代理端显示的使用次数、已用完状态和有效激活数始终一致。代理看到的次数存放在 `activation_code.seen_count`，管理员的口令列表同时显示实际次数和代理看到的次数。

### 二级代理

管理员允许后，一级代理可以在代理后台开设二级代理：分配口令（口令仍归一级代理，激活也计入一级代理名下）、设置扣量和数据更新方式（不能比上级更实时）、授权查看设备记录（上级自己能看才能授权），以及停用、删除二级代理，或以二级代理的视角查看数据。二级代理看到的数据，是上级看到的数据中属于它的部分，再按它自己的档位扣量。

### 公告

管理员可以向全部代理（含二级代理）或只向一级代理发布公告，可以置顶，标为「重要」的公告会以横幅形式显示在代理后台概览顶部，后台能看到每条公告的已读人数。一级代理也可以向自己的二级代理发公告。

### 代理后台

代理后台的内容：

- 概览：累计、今日、近 7 天和本月的有效激活，均带环比。
- 趋势图：可以查看近 7 / 14 / 30 / 90 天、本月、上月或自定义日期，最长 366 天，超过 92 天时按月显示。
- 其他统计：按月统计，以及每个口令、每个二级代理的激活数。
- 激活记录：能查看明细的代理可以按筛选导出 CSV，设备号和 IP 已脱敏。
- 其他页面：7 日留存、公告、口令申请。
- 账号：代理可以修改密码，连续输错 5 次后暂停 15 分钟。

## 管理后台

### 管理员与权限

| 角色 | 权限 |
| --- | --- |
| 超级管理员 | 所有 App 和所有权限，管理员管理、管理令牌、系统配置、新建和删除 App、从备份新建 App、清空日志 |
| 成员 | 只能看到分配给自己的 App，在每个 App 上按需授予以下权限 |

| App 权限 | 允许的操作 |
| --- | --- |
| 发布版本 | 上传、发布、灰度、回滚、删除版本，管理该 App 的发布令牌 |
| 切换 A/B 面 | 切换运行模式 |
| App 设置 | 渠道、测试设备、Webhook、群机器人、口令接口密钥、增量更新 |
| 签名与备份 | 更换签名密钥、复用其他 App 的密钥（两个 App 都需要此权限）、下载和恢复备份 |

另有两项全局权限：「口令与激活」（新建、编辑、导入、删除口令，导出激活记录，审核口令申请）和「管理代理」，因为口令和代理不属于单个 App。

关于权限的规则：

- 能查看任意一个 App 的成员都能看口令列表，但激活记录只显示其有权限的 App。
- 权限在服务端校验，没有权限的按钮不显示。
- 权限修改立即生效。成员被停用、重置密码或删除后，已登录的会话在下一次请求时退出。
- 系统中至少保留一个启用的超级管理员；不能停用、降级或删除自己。
- 下载备份、删除 App 时需要输入登录密码。

### 登录与安全

- 会话保存在数据库的 `spring_session` 表中，重启服务或更换 jar 后不用重新登录。Cookie 名为 `OTA_SESSION`。
- 勾选「记住我」时保持登录 30 天，不勾选时空闲 1 天后退出，两项时长都可以调整。
- 两步验证使用身份验证器动态码，开启时生成 8 个一次性恢复码。同一个动态码只能用一次，连续输错 5 次需要重新输入密码。可以要求所有管理员开启，超级管理员可以重置他人的两步验证。
- 每个账号默认最多同时在 10 台设备上登录（可选 1 / 2 / 3 / 5 / 10 / 20）。达到上限后再登录，需要先选择退出哪几台设备。
- 登录失败限制：默认 15 分钟内同一 IP 同一账号输错 5 次，或者同一 IP 累计输错 20 次，暂停登录 15 分钟。次数和时长可以调整；同一 IP 更换账号尝试的上限是单账号次数的 4 倍，最少 20 次。
- 新建成员或重置密码时，默认要求下次登录先修改密码。
- 每个人可以查看自己的登录设备和最近 10 次登录记录（不记录 IP），也可以退出其他设备。

以上设置在「系统配置 → 登录安全」中修改。

### 演示环境

在登录页输入 `demo / demo2026`（可以在「系统配置 → 登录安全 → 演示账号」中修改或关闭）会进入演示环境。演示环境是在同一进程中另起的一个应用，数据单独存放在数据目录的 `demo` 下，不影响正式数据。

- 默认数据：40 个 App，近两个月四万多条激活，12 个代理。
- 生命周期：首次登录时准备数据，需要几秒；30 分钟无人使用自动停止；数据超过一天后，下次启动时恢复默认；准备数据时把时间平移到当天。
- 演示环境里不能修改账号安全设置、域名、存储，不能重新安装、恢复整个项目或拉取外部链接；Webhook 和群机器人只记录不发送；单个文件最大 60 MB。
- 使用演示账号登录不影响正式环境中同名的账号。

### 概览、大屏与搜索

- 当前概览：针对当前 App 的看板，共 33 张卡片可选。可以拖动排序，宽度按 12 列调整，也可以调整高度，支持键盘操作。布局、便签和今日目标存在个人账号上。页面每 30 秒自动刷新；打开弹窗或正在输入时暂缓刷新。
- 所有 App：汇总全部 App 的设备、激活和崩溃数据，列出需要注意的 App。
- 数据大屏：可以查看单个 App 或全部 App，每 10 秒刷新，有深色和浅色两种主题；分辨率 1200 × 700 以上时一屏显示完整。
- 大屏分享：生成免登录的分享链接 `/s/{token}`。
  - 有效期可选 1 小时、1 天、7 天、30 天或长期，可以设置 4 到 32 位访问密码。
  - 输对密码后，浏览器最长记住 30 天；同一 IP 10 分钟内输错 8 次会被锁定。
  - 分享页的数据按分享人当前的权限读取，分享人被停用或失去 App 权限时链接失效。
  - 每人最多同时有 50 个有效分享；演示环境不能分享。
- 待处理：汇总代理口令申请、启动失败偏多的版本、签名异常、从未下载过备份、接口地址缺少端口等事项。顶栏铃铛显示所有 App 的待处理，概览只显示当前 App 的；每 30 秒刷新，数量同时显示在浏览器标签标题上。
- 搜索：按 `Ctrl K`（macOS 为 `⌘K`）打开，可以跳转页面、执行操作，也可以搜索口令、设备、版本、代理、成员和 App，只返回有权限查看的结果。

### 外观与语言

超级管理员在「系统配置 → 外观」中设置：

- 后台名称：最多 20 字，产品介绍页显示时去掉末尾的「管理后台」。
- 登录页标语。
- 一键风格：12 套。
- 主题色：24 种，深色模式下自动调整。
- 其他：圆角、侧栏样式、页面宽度、卡片样式、页面背景、按钮和表格样式。

这些设置对后台、代理后台和登录页统一生效。深色模式、信息密度、侧栏、动画开关由每个人在外观菜单中选择，存在个人账号上，换设备登录后保持一致。

界面支持中文和英文，在顶栏切换。英文词典在 `frontend-vue/src/i18n`，只有选择英文时才加载。代理名称、备注、版本说明等用户数据保持原样。

### 前端与版本提示

- 加载方式：页面先返回加载壳，页面数据由脚本取回后渲染，所以浏览器「查看源代码」只能看到加载壳。后台页面的脚本和样式只发给已登录的用户。
- 字段过滤：服务端只发送页面用到的字段，密码和密钥类字段永远不发送。
- 安全：页面没有内联脚本，响应头带 CSP。
- 缓存与预取：脚本和样式按内容哈希长期缓存；切换页面时只请求页面数据，鼠标停在链接上时提前获取。
- 动画：只受个人偏好中的动画开关控制，不跟随操作系统的「减弱动态效果」设置。
- 新版本提示：后台页面每 10 秒请求一次 `/app/version`。替换 jar 并重启服务后，已打开的页面会提示重新加载；页面上有未保存的输入时，会先提醒保存。

## 运维

### 健康检查与运行信息

`GET /healthz` 正常时返回 200 `{"status":"ok"}`，数据库连接失败时返回 503，可以用于负载均衡或网站监控。

「系统配置 → 运行信息」显示以下内容：

- 版本和运行时长；
- 内存；
- 数据目录所在磁盘的剩余空间，不足 2 GB 时提示；
- Java 和操作系统版本。

「复制诊断信息」会把这些内容复制成一段文本，不含密码和密钥。

### Prometheus 监控指标

在「系统配置 → 运行信息 → 监控指标」生成监控令牌后，用请求头 `Authorization: Bearer otm_…` 请求 `GET /api/metrics`，获取 Prometheus 文本格式的指标。

- 管理令牌不能读取指标。
- 重新生成令牌后，旧令牌立即失效；关闭该功能后接口返回 404。
- 指标最多每 10 秒计算一次。
- 生成令牌的弹窗里提供了 `prometheus.yml` 采集配置。

| 指标 | 说明 |
| --- | --- |
| `ota_up`、`ota_build_info{version}`、`ota_apps` | 服务运行状态、版本号、App 数 |
| `ota_app_info{app,name}`、`ota_app_side_b{app}` | App 名称、运行模式（B 面为 1） |
| `ota_devices_active_30d{app}` | 近 30 天检查过更新的设备数 |
| `ota_activations_confirmed_total{app}`、`ota_activations_today{app}` | 累计和今日有效激活 |
| `ota_launch_errors_24h{app}` | 近 24 小时上报的启动错误 |
| `ota_release_rollout_percent`、`ota_release_offered_total`、`ota_release_installed_total`、`ota_release_failed_total`、`ota_release_failure_ratio` | 各渠道线上版本的灰度比例、推送数、装上数、启动失败数、失败率（标签：`app`、`channel`、`runtime`、`release`） |
| `ota_channel_embedded{app,channel,runtime}` | 渠道已回退到安装包内置版本时为 1 |
| `ota_code_requests_pending` | 待审核的口令申请数 |

告警规则示例：`ota_release_failure_ratio > 0.1 and ota_release_failed_total >= 5`，持续 10 分钟。

### 备份与恢复

App 备份在「App 设置 → 备份与恢复」中下载，包含以下内容：

- 签名私钥和证书；
- 口令接口的 App Key 和密钥、授权签名密钥；
- Webhook、群机器人、渠道、测试设备；
- 全部口令。

备份用自行设置的备份密码加密（PBKDF2 + AES-256-GCM），下载和恢复都需要先输入登录密码。版本文件和激活记录不在 App 备份中。用途有两种：

- 换服务器：在新服务器的「所有 App → 从备份恢复」中恢复，已安装的 App 和用户已有的授权继续有效。
- 密钥被误换：在原服务器上勾选「覆盖」恢复。

项目备份在「系统配置 → 备份」中管理，仅限超级管理员：

- 完整备份：把数据库、版本文件和图标、签名私钥、主密钥、安装配置打包成 `.otaproj` 文件，用备份密码加密（PBKDF2 + AES-256-CTR + HMAC）。服务器先把文件完整写到 `tmp/downloads` 再开始下载，下载完成或一小时后自动删除。数据库是 MySQL 时，请另外用 mysqldump 备份；文件存在 S3 时不会打包进备份。完整备份只能在后台输入登录密码后下载，管理接口不提供，避免令牌泄露时私钥一并泄露。
- 自动备份：每天定时在 `backups/` 下保存一份（不加密），保留最近若干份；列表中的每一份都可以下载（下载时加密）、恢复或删除。如果要异地保存，可以用 rsync 等工具同步该目录，同步目标需要同样保密。
- 恢复：上传 `.otaproj` 文件（分片上传）或者选择服务器上的一份，输入备份密码和登录密码。
  - 检查通过后服务在进程内重启，在打开数据库之前替换数据（`RestoreOnStart`），所有人需要重新登录。
  - 原数据移到 `restore/before-时间` 下，保留最近两份；恢复失败时自动换回原数据。
  - 解密和检查在后台进行，大备份不会因为反向代理超时而失败。

使用宝塔 WAF 时，需要把 `/admin/settings/backup/restore` 和 `/admin/apps/restore` 加入 URL 白名单，否则加密内容可能被当作攻击拦截。

### 文件存储

在「系统配置 → 存储 → 切换存储」中，可以在本机存储和 S3 兼容对象存储之间切换，支持阿里云 OSS、腾讯云 COS、七牛、MinIO、Cloudflare R2、AWS S3。

切换前先点「测试连接」：服务器会写入一个测试文件并读回，再不带签名从下载地址下载一次，最后删除。存储桶不是公共读、或者 CDN 没配好时，测试不通过，也不允许切换。填写时注意：

- 服务地址填地域节点，例如 `https://oss-cn-hangzhou.aliyuncs.com`，不要带存储桶名；误填存储桶域名时会自动去掉存储桶名。
- 服务地址是 IP 时，自动使用路径风格访问。
- 区域一般不用填；AWS S3 需要填，填错时测试结果会提示正确的值。

切换过程：

1. 把所有版本文件、补丁和安装包复制到新存储，每个文件先核对 SHA-256 再写入。新存储里已有的文件跳过，中途失败可以继续。
2. 复制完成后立即改用新存储，补齐切换期间新上传的文件，并写入 `install.json`。原存储中的文件不会删除。

原存储已经无法访问时，服务器先检查新存储里有哪些文件：

- 文件齐全，直接切换。
- 有缺失，弹窗说明哪些版本和安装包会被清空，确认后再切换。被清空的版本不再下发，重新上传相同的包即可恢复。

文件存储写在启动参数或环境变量（`--ota.storage.type` 等）中时，以启动参数为准，后台不能切换。

### 清理与删除

- 清理无用文件：「系统配置 → 存储」显示用量。「清理无用文件」删除 24 小时前登记、且没有任何版本使用的文件和补丁，对象存储中的对应文件也一并删除。
- 删除 App：在「App 设置 → 删除 App」中操作，仅限超级管理员，需要输入 App 标识和登录密码。
  - 一并删除：版本、渠道、该 App 的激活记录、发布令牌、设备统计、测试设备、版本统计和启动错误，以及成员对它的授权。
  - 保留：口令、代理账号和操作日志。
  - 管理接口：`DELETE /api/v1/apps/{app}?confirm={app}`。删除前建议先下载 App 备份。

### 操作日志

所有操作都会记录操作人和对应的 App。日志可以按类别、App 和时间范围筛选，并按当前筛选导出 CSV；类别包括版本与发布、运行模式与计划、口令与激活、代理、App 设置、账号与登录、系统。保留期可以设为一直保留，或者 90 / 180 / 365 天，到期后每天凌晨自动清理。

## 部署

### 宝塔面板 / Nginx 反向代理

1. 安装 Java 17。
2. 把 `ota-platform.jar` 上传到服务器，例如 `/www/ota-platform/`。如果用配置文件代替安装引导，把 `deploy/application-prod.example.yml` 复制成同目录的 `application-prod.yml`，启动时加上 `--spring.profiles.active=prod`。
3. 在「Java 项目管理」中添加项目，启动命令：

   ```bash
   java -Xmx1g -jar /www/ota-platform/ota-platform.jar --server.address=127.0.0.1
   ```

   `--server.address=127.0.0.1` 让 8812 端口只接受本机 Nginx 的连接。不加的话，如果防火墙没有拦截 8812，外网可以绕过 Nginx 和 HTTPS 直接访问后台，密码会明文传输，登录失败限制也可能被绕过。

4. 为站点配置反向代理到 `http://127.0.0.1:8812`，并加上：

   ```nginx
   client_max_body_size 200m;          # 后台上传 ZIP 更新包；安装包走分片上传，不受此限制
   proxy_read_timeout 300s;            # 命令行和接口添加外部链接版本时，要在请求内读取全部文件
   proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
   proxy_set_header X-Real-IP $remote_addr;
   proxy_set_header X-Forwarded-Proto $scheme;
   ```

   登录失败限制按 `X-Forwarded-For` 中最后一个地址识别 IP，因此需要保留这几行 `proxy_set_header`。

5. 打开站点地址完成安装引导，绑定的域名应与反向代理的域名一致。

后台跳转使用相对地址，以带端口的地址访问时（例如 `https://域名:8813`），登录过期后也会回到带端口的地址。网站监控或负载均衡可以探测 `GET /healthz`。

### 升级

先停止服务，再替换 jar，再启动。也可以把新 jar 上传成其他文件名，用 `mv` 覆盖后重启。不要在服务运行时直接覆盖正在使用的 jar，否则运行中的程序会因为读不到原来的类而出错；万一覆盖了，程序会尽快把数据写入磁盘并在日志中提示，重启后数据完整。

- 数据库表和字段在启动时自动补齐，一般不需要手动执行 SQL；需要手动执行的调整放在 `deploy/sql/`。
- 同一个 jar 重启时跳过表结构检查（Hibernate `ddl-auto=update` 在 MySQL 上需要逐表查询列和索引），换了 jar 后第一次启动才检查。检查过的版本记在 `app_setting` 表的 `schema.build` 中。
- 从没有安装引导的旧版本升级时，第一次启动会根据现有数据自动标记为已安装、生成 `install.json`（沿用原来的启动参数），原后台账号自动成为超级管理员，密码不变。

## 配置参考

以下配置都可以在安装引导中填写。写在启动参数、环境变量或配置文件中的值优先级更高。完整示例见 `deploy/application-prod.example.yml`。

| 配置项 | 说明 | 默认值 |
| --- | --- | --- |
| `server.port` | 监听端口 | `8812` |
| `ota.public-url` | App 和浏览器访问的地址，清单中的下载地址以它为前缀 | `http://localhost:8812` |
| `ota.data-dir` | 数据目录 | `./data` |
| `ota.master-key` / `OTA_MASTER_KEY` | 主密钥，32 字节 Base64（`openssl rand -base64 32`） | 自动生成到 `data/master.key` |
| `ota.admin-password` / `OTA_ADMIN_PASSWORD` | 设置后跳过安装引导，直接创建管理员 `admin` | 空 |
| `ota.bootstrap-token` / `OTA_BOOTSTRAP_TOKEN` | 初始管理令牌 | 首次启动随机生成，在日志中打印一次 |
| `ota.display-zone` | 后台显示时间所用的时区 | `Asia/Shanghai` |
| `ota.max-asset-bytes` | 单个文件上传上限（字节） | 200 MB |
| `ota.min-confirm-ms` | 兑换后多少毫秒内确认算作刷量，0 为关闭 | `2000` |
| `ota.storage.type` | `local` 或 `s3` | `local` |
| `ota.storage.s3.*` | `endpoint`、`region`、`bucket`、`access-key`、`secret-key`、`path-style`、`prefix`、`public-url`（CDN 地址） | 区域 `us-east-1`，前缀 `ota/` |
| `ota.patch.enabled` / `bases` / `max-ratio` | 增量更新开关、为最近几个版本生成补丁、补丁大小上限占完整文件的比例 | `true` / `3` / `0.8` |
| `ota.legacy.app` / `shared-key` / `token-secret` | 已发布旧安装包的兼容入口（兑换、凭证校验、激活确认、`/api/manifest`），三项都配置后才开启 | 空 |
| `ota.login.max-devices` | 每个管理员最多同时登录的设备数，在后台修改后以后台设置为准 | `10` |
| `spring.datasource.*` | 数据库连接 | H2 文件库 `data/db/ota` |

对象存储密钥和旧版兼容密钥也可以用环境变量传入：`OTA_S3_ACCESS_KEY`、`OTA_S3_SECRET_KEY`、`OTA_LEGACY_SHARED_KEY`、`OTA_LEGACY_TOKEN_SECRET`。

## 开发

在新电脑上配置环境、打包、测试和部署的步骤，见 [README-开发说明.md](README-开发说明.md)。

```bash
scripts/setup-toolchain.sh       # 安装 JDK 17、Maven、Node.js（不需要 sudo）
./build.sh                       # 输出 target/ota-platform.jar
tests/run.sh                     # 全量回归，见 tests/README.md
node cli/bin/ota.mjs help
```

只改了 Java 代码时，可以直接 `mvn -q clean package -DskipTests`，前端打包结果已经提交在 `src/main/resources/static/vue` 中。只打包前端：`cd frontend-vue && npm run build`。

### 服务端结构

代码位于 `src/main/java/com/ota/platform`，按业务分包：

| 包 | 职责 |
| --- | --- |
| `manifest`、`patch` | App 使用的接口：检查更新、增量补丁 |
| `release`、`pkg`、`installer` | 版本与发布、更新包导入与校验、安装包解析 |
| `ota`、`stats`、`webhook` | 设备统计、启动失败、模拟检查更新、事件通知与发送记录 |
| `codes` | 口令、激活记录、口令接口 |
| `agent`、`notice` | 代理账号、口令申请与审核、公告 |
| `app`、`signing`、`backup` | App 与渠道、App 图标、签名密钥、App 备份（`BackupService`）、项目备份（`ProjectBackupService`、`RestoreOnStart`） |
| `schedule` | 计划任务 |
| `demo` | 演示环境（`DemoSandbox`）、请求转发（`DemoProxyFilter`）、演示环境限制（`DemoGuard`） |
| `admin`、`security`、`auth` | 管理员与权限、登录与两步验证、API 令牌 |
| `settings`、`storage`、`install` | 系统配置与主题（`ThemeCatalog`、`SettingService`）、文件存储、安装引导 |
| `api` | 管理接口 |
| `web.admin`、`web.agent` | 后台和代理后台的页面控制器 |
| `web` | 公共部分：显示格式（`AdminUi`）、CSV 导出、产品介绍页、健康检查 |
| `web.page` | 页面交付：加载壳（`VueUi`）、页面数据（`PageData`）、版本号（`BuildStamp`） |
| `audit`、`common`、`config` | 操作日志、公共工具、Spring 配置 |

### 前端结构

后台前端位于 `frontend-vue`，使用 Vue 3 和 Vite，打包输出到 `src/main/resources/static/vue`：

| 目录 | 内容 |
| --- | --- |
| `src/views` | 页面组件（`pages/`）和公共片段（`frags/`）。模板表达式按 Java 的规则求值（`src/runtime`），数字和日期的显示与服务端一致 |
| `src/behaviors` | 页面交互：`ui.js` 负责弹窗、引导、标签栏、搜索，`pages/` 是各页面自己的脚本 |
| `src/main.js` | 获取页面数据、切换页面、提交表单、前进后退 |
| `src/css` | 样式。登录页、安装页、错误页的样式打包到 `assets/`（公开），后台样式打包到 `app/`（需要登录） |
| `src/i18n` | 英文词典。运行 `node tools/i18n-extract.mjs` 列出尚未翻译的句子 |

控制器照常返回页面名和模型，`PageData` 只把页面用到的字段转成 JSON 发给浏览器。字段清单 `src/main/resources/vue-fields.json` 在 `npm run build` 时由 `tools/fields.mjs` 从组件中统计生成，组件用到新字段后需要重新打包。`npm run build:ssr` 和 `npm run ssr` 用于测试中的服务端渲染，不进入 jar。
