# OTA Platform

自托管的 Expo 热更新服务，带口令激活、代理和后台管理。

- **热更新**：兼容 Expo Updates 协议 v0 / v1，App 只改 `app.json` 就能接入。多 App、多渠道、灰度、回滚（默认回到上一版本，也可以选更早的任意版本）、回退到安装包内置版本；常规更新和口令更新可以发不同的包（同一个检查更新地址，新装 App 输入口令激活时拿单独设的口令更新包）；每个渠道的发布记录；每个 App 独立的代码签名密钥。
- **增量更新**：发布后为最近几个版本生成启动包的 bsdiff 补丁，设备只下载差异（expo-updates 内置支持，补丁打不上会自动改下完整文件）。
- **发布监控**：每个版本的安装漏斗（推送 / 装上 / 启动失败）、启动崩溃信息、增量补丁省下的流量；启动失败偏多时告警（Webhook + 钉钉 / 飞书 / 企业微信群机器人），一键回滚。全部来自 expo-updates 自动带的请求头，App 不用写代码。
- **测试与排查**：测试设备（指定设备改用测试渠道，不用重新打包）、「推到其他渠道」（测试渠道验证好原样发到 production）、模拟检查更新（按设备的真实条件走一遍服务器的判断，说明它会拿到什么、为什么）。
- **多管理员**：超级管理员和成员；成员按 App 分配，每个 App 单独勾选发布版本、切换 A/B 面、App 设置、签名与备份；口令与激活、管理代理不分 App，单独授权。服务端校验，没权限的按钮不显示；停用、改密码、删除后已登录的会话立即失效；日志记录操作人和 App。
- **文件存储**：按 SHA-256 存储，同样的文件只存一份、只传一次。本机磁盘，或任意 S3 兼容对象存储（阿里云 OSS、腾讯云 COS、七牛、MinIO、Cloudflare R2、AWS S3），App 从 CDN 下载。装好以后在「系统配置 → 存储」随时切换，已有文件自动搬过去并逐个核对哈希。
- **发布方式**：命令行一条命令发布（适合 CI），或在后台上传 ZIP、添加放在 CDN 上的 dist 目录链接。
- **安装包校验和更新包结构**：可以上传 APK / IPA（可选），自动读出包名、版本、Runtime、更新地址、渠道和内置证书，和服务器配置逐项比对，版本「校验」时一起检查；版本详情里能看更新包的完整文件清单（外部链接版本也能看），和任意旧版本对比，标出新增、有变化、没变的文件和走增量补丁的启动包。
- **口令**：口令所有 App 通用，一个口令在哪个 App 里都能兑换，使用上限合起来算；同一台手机所有 App 加起来只算一次激活（按设备指纹去重）。独立的口令接口（HMAC 签名、防重放），批量生成或导入已有口令、使用上限、有效期、绑定渠道、兑换开关、Webhook 通知；后台按状态、代理、关键字筛选，批量启用、停用、分配、删除。激活记录按 App、代理、时间段、设备筛选，带对账汇总，导出就是对账明细。设备列表、代理列表、单个代理的激活记录也都能导出（口令列表本身不提供导出）。
- **代理**：代理账号和代理后台，口令归属代理，代理端的可见范围、数据更新方式和扣量档位。可以让代理自己申请口令：不能申请、需要审核、自动通过，每天有上限；后台集中审核（可以改个数和次数，支持批量），勾选多个代理批量设置申请方式、启用停用和删除；删除代理时可以连 TA 的口令和激活记录一起删。
- **后台**：所有 App 看板（全部 App 的设备、激活、崩溃汇总和「需要注意」）、数据大屏（一个 App 或全部 App，每 10 秒更新，深色 / 浅色两套，可以生成不用登录就能看的分享链接）、当前概览（可以拖动排序、改宽度、添加和收起卡片的看板，每个人各存一份：待处理、运行模式、激活和设备看板、计划任务、激活时段、今日目标、便签等 33 张卡片）、口令、激活记录、代理（含每个代理、口令的日活与留存）、版本发布（安装情况、告警、版本详情、编辑、强制更新）、设备统计（版本分布、启动错误、诊断、测试设备）、App 设置、签名配置（可复用其他 App 的密钥，显示哪些 App 共用证书）、管理账号、我的账号、操作日志、系统配置、API 文档；24 种主题色、12 套一键风格。
- **运维**：App 加密备份和恢复、删除 App 和渠道、存储用量和无用文件清理、健康检查 `/healthz`、Prometheus 监控指标 `/api/metrics`、登录失败次数限制、全部操作记日志（可搜索）。令牌只在创建时弹窗显示一次，倒计时结束才能关闭，列表里只显示开头几位。
- **安装引导**：启动命令不用带任何参数，第一次打开网页按引导填数据库（推荐 MySQL，内置数据库适合试用；已有数据可选保留或清空）、访问域名（多个域名，可以带端口，后台和接口可以分开绑定）、文件存储和超级管理员。之后在「系统配置」里修改访问域名、切换文件存储，验证密码后可以重新进入引导。
- **登录与安全**：登录会话存在数据库里，重启服务不用重新登录；「记住我」保持登录天数、空闲退出时间、密码输错几次暂停多久、每人最多同时登录几台都可设置；两步验证（身份验证器动态码 + 一次性恢复码，可以要求所有管理员开启，超级管理员可重置）；新成员首次登录要求修改初始密码；登录设备列表和「退出其他设备」；登录记录（不记 IP）。操作日志可按类别（版本与发布、运行模式与计划、口令与激活、代理、App 设置、账号与登录、系统）、App 和时间范围筛选，按当前筛选导出 CSV，可以设置保留多久（到期每天凌晨自动清理）。
- **官网**：根路径（域名后面不带路径）是产品官网：黑白为主、排版为主的浅色页面；首屏右边是一段产品演示（光标点「发布」→ 灰度 → 手机灵动岛里收到更新、首页换新 → 全量，循环播放，滚走了就停），下面是功能（列表 + 那个功能在后台里的样子，自动轮播）、接入三步、安全，中英文切换（和后台用同一个语言设置），动画在打开了系统「减弱动态效果」的电脑上也照样播，独立的静态页面，打开就有；后台在 `/admin`，代理端在 `/agent`，登录在 `/login`。官网上的名字取后台名称去掉「管理后台」。
- **前端**：Vue 3。打开任何页面先显示加载动画，页面数据由脚本取回后渲染，查看源代码只有一个加载壳；脚本按内容哈希长期缓存，切换页面只取页面数据（鼠标停在链接上时预取），秒开。所有页面适配手机：表格变卡片、对话框从底部弹出。动画只看「偏好 → 动画」这一个开关：电脑系统的「减弱动态效果」（很多 Windows 电脑关了系统动画效果、远程桌面、虚拟机会打开它）不管，后台、代理后台、登录页、数据大屏、分享页、官网都照样动。

## 快速开始

需要 Java 17；打包需要 Maven 和 Node.js 18+。

```bash
./build.sh                       # 先打包后台前端（压缩、去注释、混淆），再打 jar
java -jar target/ota-platform.jar
```

用浏览器打开 `http://你的地址:8812`，按安装引导填写：

1. **数据库**：推荐 MySQL（先建好空库），正式使用请选它；内置数据库开箱即用，适合试用。库里已经有数据时选「保留」或「清空」，清空要再输入「清空」确认。
2. **访问域名**：可以填多个域名，每个域名勾选用于「后台」「接口」或两者，域名可以带端口（比如 `app.example.com:8813`）。打开「只允许这些域名访问」后，用错域名访问一律 404：只绑了后台的域名调不了接口，只绑了接口的域名打不开后台。`127.0.0.1` / `localhost` 始终能用，不会把自己锁在外面。对外地址（App 下载文件、API 文档和接入配置里显示的地址）默认取第一个接口域名，带端口时地址里也带同样的端口。反向代理（宝塔的 Nginx 默认 `Host $host`）会把端口去掉，所以安装引导按浏览器地址栏里的域名（带端口）预填；对外地址和某个接口域名是同一个主机、却漏了端口时，保存时自动补上，「系统配置 → 安装与域名」里也会提示并一键改好。
3. **文件存储和高级设置**：本机存储或 S3 兼容对象存储（以后可以在系统配置里切换）；后台显示时区。
4. **超级管理员**：账号和密码，之后在「管理员」里给同事建成员账号。

提交后服务自动重启（十几秒），配置写在 `data/install.json`，密码和密钥用主密钥加密保存。装好以后在「系统配置 → 安装与域名」修改访问域名和对外地址（立即生效，不用重启），在「系统配置 → 存储」切换文件存储；验证自己的密码后也可以重新进入安装引导（改数据库等）。

Docker、脚本部署可以跳过页面：带上环境变量 `OTA_ADMIN_PASSWORD` 启动就直接装好（账号 `admin`），`OTA_BOOTSTRAP_TOKEN` 指定一个管理令牌。启动参数和环境变量的优先级高于 `install.json`。

数据都在 `./data`（`--ota.data-dir` 修改）：

| 路径 | 内容 |
| --- | --- |
| `db/` | 默认的 H2 数据库（生产环境建议 MySQL） |
| `blobs/` | 本机存储的文件 |
| `master.key` | 主密钥，加密各 App 的签名私钥、两步验证密钥和 `install.json` 里的密码。**丢了就解不开，务必备份**；生产环境建议改用环境变量 `OTA_MASTER_KEY` |
| `install.json` | 安装引导保存的配置（数据库、域名、存储等），只有运行账号能读写 |

### Docker

```bash
docker compose -f deploy/docker/docker-compose.yml up -d
```

修改 `deploy/docker/docker-compose.yml` 里的 `OTA_PUBLICURL`；需要 MySQL 时取消对应注释。数据在项目根目录的 `data` 下。只打镜像：`docker build -f deploy/docker/Dockerfile -t ota-platform .`。

## 接入 App

1. 后台「所有 App」新建 App：填 App 的真实名称（用户手机上看到的名字），可以填下载链接（App Store 或官网下载页，在 App 设置里查看和复制）；新 App 自动生成密钥，已发布、内置了证书的 App 导入当时的密钥对。
2. 在「App 设置」下载证书放到 `certs/certificate.pem`，修改 `app.json`，重新打包：

```json
{
  "expo": {
    "runtimeVersion": { "policy": "appVersion" },
    "updates": {
      "url": "https://ota.example.com/m/my-app",
      "requestHeaders": { "expo-channel-name": "production" },
      "codeSigningCertificate": "./certs/certificate.pem",
      "codeSigningMetadata": { "keyid": "main", "alg": "rsa-v1_5-sha256" }
    }
  }
}
```

## 发布

```bash
cd cli && npm link            # 或者直接 node cli/bin/ota.mjs
ota login --server https://ota.example.com --token ota_xxx
cd 你的 App 目录
ota publish --app my-app --message "修复登录页"            # 导出、只传有变化的文件、发布到 production
ota publish --app my-app --channel staging --rollout 20    # 指定渠道和灰度比例
ota publish --app my-app --as activation                   # 发成口令更新：新装 App 输入口令激活时下载它
ota activation clear --app my-app --runtime 1.0.0          # 取消口令更新包，激活时改回拿常规更新包
ota rollback --app my-app --runtime 1.0.0                  # 回滚到上一版本
ota rollback --app my-app --runtime 1.0.0 --to 4a55bc34    # 回滚到更早的任意版本（版本 ID 前 8 位即可）
ota installer upload --app my-app ./app.ipa --note "应用商店 1.0.0"   # 上传安装包（自动分片），显示检查结果
ota schedule rollout --app my-app --runtime 1.0.0 --percent 50 --at "2026-11-13 10:00"   # 定时调整灰度
ota schedule mode --app my-app --face B --at "2026-11-13 20:00"     # 定时切到 B 面（要管理令牌）
ota schedule list --app my-app                                      # 等执行和最近执行过的计划
```

CI 里用发布令牌（后台「App 设置 → 发布令牌」创建，只能操作一个 App），通过环境变量 `OTA_SERVER`、`OTA_TOKEN` 传入。管理所有 App 的管理令牌在「系统配置 → 管理令牌」里，下面的「怎么用」有命令行和 curl 两段示例（用的是这台服务的地址）。

全部接口见后台「API 文档」。

## 配置

| 配置项 | 说明 |
| --- | --- |
| `ota.public-url` | App 和浏览器访问的地址，清单里的下载地址以它为前缀 |
| `ota.data-dir` | 数据目录 |
| `ota.master-key` / `OTA_MASTER_KEY` | 主密钥，32 字节 Base64（`openssl rand -base64 32`）。不配置时自动生成到 `data/master.key` |
| `spring.datasource.*` | 数据库。默认 H2 文件库；MySQL 见 `deploy/application-prod.example.yml` |
| `ota.storage.*` | 文件存储，`type: local` 或 `s3` |
| `ota.patch.*` | 增量更新：开关、为最近几个版本生成补丁、补丁大小上限 |
| `ota.login.max-devices` | 每个管理员最多同时在几台设备上登录，默认 10；在「系统配置 → 登录安全」里改过以后以那里为准 |

这些都可以在安装引导里填，不用写配置文件；写在启动参数或配置文件里的优先级更高。完整示例见 `deploy/application-prod.example.yml`。

## 部署到宝塔

1. 安装 Java 17（宝塔「Java 项目管理」或系统包管理器）。
2. 上传 `ota-platform.jar` 和 `application-prod.yml` 到同一目录，比如 `/www/ota-platform/`。
3. 「Java 项目管理」→ 添加项目，启动命令：

```bash
java -Xmx1g -jar /www/ota-platform/ota-platform.jar --server.address=127.0.0.1
```

同一个 jar 再重启时不再检查表结构（Hibernate 的 ddl-auto=update 在 MySQL 上要把每张表的列和索引查一遍），换了 jar 以后第一次启动才检查、补齐，检查过的版本记在 `app_setting` 的 `schema.build`。

`--server.address=127.0.0.1` 让 8812 端口只给本机的 Nginx 访问：不加的话，服务器防火墙没拦 8812 时，外网能绕过 Nginx 和 HTTPS 直接用 HTTP 访问后台（密码明文传输，登录失败次数限制也能被绕过）。启动后打开网站地址，按安装引导完成设置（绑定的域名要和反向代理的域名一致）。

4. 网站 → 反向代理到 `http://127.0.0.1:8812`，并在配置文件里加上：

```nginx
client_max_body_size 200m;          # 后台上传更新包 ZIP；安装包（APK / IPA）分片上传，不受这个限制
proxy_read_timeout 300s;            # 命令行、接口添加外部链接时在请求里把文件读一遍；后台页面是先在后台读、显示进度，不受这个限制
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
```

后台跳转用的是相对地址，带端口访问（比如 `https://域名:8813`）时，登录过期也会回到带端口的地址。

宝塔的网站监控或负载均衡可以探 `GET /healthz`：正常返回 200 `{"status":"ok"}`，数据库连不上返回 503。「系统配置 → 运行信息」能看到版本、已经运行多久、内存、数据目录所在磁盘的剩余空间（不到 2 GB 会提示）、Java 和系统版本；「复制诊断信息」把这些复制成一段文字，找人看问题时直接发过去（不含密码和密钥）。

后台登录有失败次数限制：默认 15 分钟内同一 IP 同一账号密码错 5 次、或同一 IP 错 20 次，暂停登录 15 分钟；次数（3 / 5 / 10 次）和时长（5 / 15 / 30 / 60 分钟）在「系统配置 → 登录安全」里改，同一 IP 换着账号试的上限是次数的 4 倍、至少 20 次，登录页提示的分钟数跟着变。IP 取 Nginx 追加在 `X-Forwarded-For` 最后的地址，所以上面两行 `proxy_set_header` 要保留。

## 监控指标（Prometheus）

「系统配置 → 运行信息 → 监控指标」点「生成监控令牌」（只显示一次）以后，`GET /api/metrics` 返回 Prometheus 文本格式的指标，请求头带 `Authorization: Bearer otm_…`。监控令牌只能读指标，管理令牌不能用来读；重新生成后旧令牌马上失效，「关闭」以后返回 404。生成令牌的弹窗里有现成的 `prometheus.yml` 采集配置。

| 指标 | 说明 |
| --- | --- |
| `ota_up`、`ota_build_info{version}`、`ota_apps` | 服务在运行、版本号、App 数 |
| `ota_app_info{app,name}`、`ota_app_side_b{app}` | App 的名字（面板上显示用）、运行模式（B 面为 1） |
| `ota_devices_active_30d{app}` | 近 30 天检查过更新的设备 |
| `ota_activations_confirmed_total{app}`、`ota_activations_today{app}` | 累计和今天的有效激活 |
| `ota_launch_errors_24h{app}` | 近 24 小时上报的启动错误 |
| `ota_release_rollout_percent`、`ota_release_offered_total`、`ota_release_installed_total`、`ota_release_failed_total`、`ota_release_failure_ratio` | 每个渠道线上版本（标签 `app`、`channel`、`runtime`、`release`）的灰度比例、推送、装上、启动失败、失败率（0 到 1） |
| `ota_channel_embedded{app,channel,runtime}` | 渠道回退到了安装包内置版本时为 1 |
| `ota_code_requests_pending` | 待审核的口令申请 |

告警规则示例：`ota_release_failure_ratio > 0.1 and ota_release_failed_total >= 5`（持续 10 分钟）。指标每 10 秒最多算一次。

## 多管理员和权限

- **超级管理员**：所有 App、所有权限，还能管理管理员、管理令牌、系统配置，新建和删除 App，从备份新建 App，清空日志。至少保留一个启用的超级管理员，不能停用、降级或删除自己。
- **成员**：只看到分配给 TA 的 App。每个 App 上有授权就能查看（App 设置里的密钥不显示），另外按需勾选：

| 权限 | 能做什么 |
| --- | --- |
| 发布版本 | 上传、发布、灰度、回滚、删除版本，管理这个 App 的发布令牌 |
| 切换 A/B 面 | 切换运行模式 |
| App 设置 | 渠道、测试设备、Webhook、群机器人、口令接口密钥、增量更新 |
| 签名与备份 | 更换签名密钥、复用其他 App 的密钥（两个 App 都要有这个权限）、下载和恢复备份 |

「口令与激活」（新建、编辑、删除、导入口令，导出激活记录，同意代理的口令申请）和「管理代理」不分 App，单独授权：口令和代理都是所有 App 共用的。能看任意一个 App 的成员都能看口令列表；激活记录只列 TA 能看的 App 的。权限改了立即生效，不用重新登录；停用、重置密码、删除后，TA 已登录的后台在下一次点击时退出。下载备份、删除 App 要输入自己的登录密码。

「管理账号」页最上面是人数、开了两步验证的、近 7 天登录过的、停用的；下面每位管理员一张卡片：角色、能操作哪些 App 和权限、能不能管口令和代理、两步验证、最近登录和备注，可以按超级管理员 / 成员 / 停用筛选、按名字账号 App 搜索。「编辑」在卡片上，「⋯」里有复制登录信息（后台地址和账号，发给新同事）、看 TA 的操作日志、停用 / 启用、退出所有设备（电脑借给了别人、怀疑密码泄露时用，密码不变）、重置两步验证和删除（自己的卡片只有前两项）。卡片最后是虚线的「新建管理员」。最下面是每项权限能做什么。

「我的账号」头部是头像、名字和角色，下面四个数字：两步验证、登录设备、能操作的 App、这台设备；内容分四个标签：资料和密码（左边名字和账号、右边改密码，下面输当前密码保存）、登录与安全、我的权限（每个 App 有哪几项，下面一行是全局权限：口令与激活、代理管理、管理账号、系统配置，没有的标成锁）、偏好（主题、侧栏、信息密度、顶部标签栏显示 / 隐藏、动画开 / 关、语言、引导）。偏好（包括右上角外观菜单里选的、语言、概览看板）存在自己的账号上，换电脑、换浏览器登录都一样；代理的偏好存在代理账号上。打开页面前就按偏好显示，不会先闪一下。升级后第一次打开时，会把这台浏览器上原来的选择存到账号上。

每个人在「我的账号 → 登录与安全」里：

- **两步验证**：用 Google / 微软身份验证器、1Password 等扫码开启，以后登录输完密码还要输 6 位动态码（同一个码只能用一次，连续错 5 次要重新输密码）。开启时给 8 个一次性恢复码，手机丢了用恢复码登录；超级管理员可以在「管理员」里重置别人的两步验证。
- **登录设备**：看到自己在哪些电脑、手机上登录着，可以退出某一台或「退出其他设备」。每个账号最多同时在 10 台设备上登录（「系统配置 → 登录安全」里可以改成 1 / 2 / 3 / 5 / 10 / 20 台）：满了以后再登录，输完密码（和动态码）会列出已经登录的设备，勾选要退出的几台才能登录，被退出的设备下次打开页面回到登录页。演示账号大家共用，不限台数。
- **登录记录**：最近 10 次成功和失败的登录（设备、浏览器、时间），不记录 IP。

超级管理员在「系统配置 → 登录安全」里设置：勾选「记住我」时保持登录几天（默认 30 天）、不勾选时空闲多久自动退出（默认 1 天）、是否要求所有管理员开启两步验证（开启后，没开的人登录后只能进「我的账号」，开启后才能用其他功能）、密码输错几次暂停登录多久、每个管理员最多同时登录几台、操作日志保留多久（一直保留 / 90 / 180 / 365 天，超过的每天凌晨清掉，保存时也清一次）。新建成员、重置成员密码时默认勾选「下次登录时要求修改密码」。

登录会话保存在数据库的 `spring_session` 表里（内置数据库和 MySQL 都会自动建表），重启服务、换 jar 都不用重新登录；Cookie 名是 `OTA_SESSION`。

## 演示账号

给客户、同事演示后台用。在登录页输 **demo / demo2026**（默认，在「系统配置 → 登录安全 → 演示账号」里改账号、密码，或者关掉）就进演示环境：一个完整的后台，带着默认的演示数据（40 个 App，每个都有图标、版本、设备和激活，近两个月四万多条激活；12 个代理和他们的口令、申请、公告、计划任务、成员），什么都能点、能上传、能改，顶栏有「演示环境」标记。

- 演示环境是同一个进程里另起的一个应用，数据单独放在数据目录的 `demo` 下，不碰正式数据；第一次有人登录时准备数据、启动（几秒），30 分钟没人用自动停掉，数据超过一天下次启动时恢复默认；「恢复默认演示数据」可以马上恢复。演示数据的时间会平移到当天，看起来就是最近的数据。
- 演示环境里不能做的：改演示账号的密码、开两步验证、让别人下线、改登录安全 / 域名 / 对外地址 / 存储、重新安装、恢复整个项目、从外部链接拉更新包；Webhook 和群机器人只记录不真的发送；单个文件最大 60 MB。
- 打开登录页或者退出，就回到正式环境。用演示账号登录不影响正式环境里同名的账号（只有演示密码对得上才进演示环境）。

## 版本回滚

「版本发布」里每个渠道的「回滚」会列出同一 Runtime 之前的所有版本，默认选中上一版本，也可以选更早的任意版本。比线上版本旧的版本会复制成一个新版本发布（内容相同），这样已经更新过的设备下次检查更新时也会换回去。要发布的就是线上的内容（线上是它的副本，或者它是线上副本的原版）时不再复制，只调整灰度；发布弹窗里会提前写明这次会不会复制。某个渠道的某个 Runtime 已经没有更新包了（回退内置版本以后把版本删了，或者取消了只设过的口令更新包），线上版本里就不再列这一行；回退内置版本的指令照常下发给还没联网的设备，重新发布这个 Runtime 的版本后又会出现。回退到安装包内置版本后，也可以直接用「回滚」选一个版本恢复。每次发布、调整灰度、回滚、回退内置版本都记在「发布记录」里，页面上列最近 10 条，更早的用 `GET /api/v1/apps/{app}/history?limit=200` 查。

**灰度不影响口令激活**：灰度按设备 ID 固定分组，组外的设备继续用上一版本。还在用安装包内置版本的设备（新装的、正在输入口令激活的）组外时同样拿上一版本，没有上一版本（第一次发布就设了灰度，或者上一版本删了）就直接拿线上版本，所以输入口令以后总能下载到一个版本、完成激活。已经装过热更新、没进灰度的设备照常不更新。「模拟检查更新」会写明这台设备按哪条规则拿到哪个版本。

**删除版本**：版本列表里除了还有设备在拿的版本都能删。不能删的是渠道的线上版本、口令更新包，以及灰度没到 100% 时其余设备拿的上一版本，这些版本的「⋯」菜单里删除换成「不能删除」并写明原因。只是留着回滚的上一版本可以删，之后回滚时选别的版本。版本文件按内容共用，删版本不删文件（「系统配置 → 存储」里可以清理没有版本在用的文件）。

## 常规更新和口令更新

每个渠道（每个 Runtime）可以发两种包，检查更新还是同一个地址：

- **常规更新**：就是线上版本。已激活的设备检查更新时拿它，可以灰度、回滚。
- **口令更新**：另外设的一个包。新装 App 输入口令激活时（设备还在用安装包内置版本）下载它，不灰度，也不受「回退内置版本」影响；它没有某个平台的文件时，这个平台的设备照旧拿常规更新包。

检查更新的地址、App 里的代码、口令接口都不用改，服务器按设备现在运行的版本区分：请求头 `expo-current-update-id` 等于 `expo-embedded-update-id`（或者没有这个头）就是还在用内置版本。**没单独设口令更新包时，激活时也拿常规更新包，和以前完全一样。**

怎么设：

- 「版本发布」页线上版本的每一行下面都有一条「口令更新」：没设时写着「跟常规更新一样」，点「单独设置」从同一 Runtime 的版本里挑一个；设了以后显示是哪个版本，可以「更换」「取消」，取消后激活时改回拿常规更新包；
- 版本列表里点「发布」，弹窗最上面选「口令更新」，选好渠道点「设为口令更新包」。弹窗里会写明这个渠道现在的常规更新包和口令更新包各是哪个版本，发布后会怎样；
- 上传更新包、添加外部链接时，「立即发布到」后面选「作为口令更新」；
- 命令行 `ota publish --as activation`、`ota deploy --release <ID> --as activation`、`ota activation clear --runtime 1.0.0`；管理接口发布时多传 `"as": "activation"`，取消用 `POST /api/v1/apps/{app}/channels/{channel}/activation/clear`。原来的调用不传这个参数，行为不变。

设、取消都记在发布记录和操作日志里，群机器人发「发布」那一类消息，Webhook 发 `release.activation_deployed`、`release.activation_cleared`。口令更新包不能删除，要删先换一个或取消。「模拟检查更新」会写明这台设备拿的是口令更新包还是常规更新包。概览的「线上版本」卡片上，设了口令更新包的渠道多一行「口令更新」。

App 只装比自己新的版本，所以口令更新包要比安装包里的版本新：重新打包安装包以后，记得换成新上传的版本，上传安装包后的「更新新旧」检查会拿口令更新包比对。设备激活以后已经在运行口令更新包，下次检查更新就按常规更新走，常规更新包比它新就会更新过去。

## 发布监控和排查

expo-updates 检查更新时会带上设备当前版本、最近启动失败的版本（`Expo-Recent-Failed-Update-IDs`）和上次崩溃的错误（`Expo-Fatal-Error`），下载文件时带上正在下载的版本。服务端据此统计：

- **推送**：检查更新时发给了多少台设备；**装上**：重启后运行这个版本的设备；**启动失败**：启动这个版本失败、自动退回之前版本的设备。至少 3 台失败且失败率不低于 5% 时，版本页、概览、所有 App 都会提示，并发一次 Webhook `release.launch_failures` 和群机器人消息。
- **启动错误**：同一台设备同样的错误 6 小时内只记一次，保留 30 天，在版本详情和设备统计里看。版本详情里还有**失败原因**：按错误的第一行归类（去掉堆栈，同一个错误在不同位置抛出算一类），列出最多的几类、各占多少、iOS / Android 各几次、最近一次是什么时候。
- **流量**：启动包按补丁、完整下载的次数，补丁省下的字节数。版本详情的安装情况是推送 → 下载 → 装上 → 启动失败。

**启动失败自动回滚**（默认不开，每个 App 单独设）：「版本发布」页线上版本标题旁边点「自动回滚」，选启动失败率达到多少（5% / 10% / 20% / 30%）、并且失败的设备至少几台（3 / 5 / 10 / 20 / 50）。线上版本的失败到了设定值，就自动回滚到上一版本，和手动回滚一样复制成新版本发布，已经更新的设备下次检查更新时也会换回去；发布记录和操作日志里操作人是「自动回滚」，群机器人发一条消息（「启动失败告警」那一类），Webhook 发 `release.auto_rollback`。每个版本只自动回滚一次，回滚后又手动发布它（会复制成新版本）就不再管；上一版本是之前自动回滚掉的、或者渠道没有上一版本时不回滚，只告警。没开时和以前完全一样：只告警。

用户说收不到更新时，在「设备统计」点这台设备的「诊断」，或点「模拟检查更新」填设备 ID。测试机先在「设备统计」里设为测试设备（改用 beta 等渠道），新版本发到 beta 验证好，在「版本发布」点「推到其他渠道」原样发到 production。测试设备可以勾**灰度白名单**：渠道灰度没到 100% 时，这台设备也先拿线上版本（比如渠道选 production，灰度刚放 5% 时自己的手机先装上验证）；不勾的照旧按设备 ID 分组。管理接口添加测试设备时多传 `rolloutFirst: true` 也行，不传就不改原来的设置。

群机器人在「App 设置 → 通知」配置，支持钉钉、飞书、企业微信（按地址自动识别），发布、回滚、回退内置版本、切换 A/B 面、启动失败告警都会通知；配好后下面可以勾选只推其中几种（比如只要启动失败告警），每个 App 单独设置。

## 待处理

「待处理」列出要你动手的事：代理的口令申请、启动失败偏多的版本、签名不对、还没下载过备份、接口对外地址少了端口。顶栏的铃铛列所有 App 的（每条写着是哪个 App 的），当前概览上的「待处理」只列当前 App 的，加上口令申请、接口地址这类不属于哪个 App 的；条目多了在卡片里滚动，不会把卡片撑高。点一下就到处理的地方（别的 App 的先切换过去），处理完自己消失；每个人只看到自己有权限的 App 和事项。页面开着时每 30 秒更新一次铃铛和侧栏「代理管理」上的数字，有新的待处理会弹一条提示，不用刷新页面；浏览器标签上也带着待处理的数，比如「(3) 当前概览」，切到别的标签页也看得到。

## 搜索和概览

按 ⌘K（Windows 上 Ctrl K）或点顶栏的搜索框：除了跳页面、执行操作，输入两个字以上会直接搜口令（所有 App 通用）、当前 App 的设备和版本，以及代理、成员和 App，点结果直接到对应的地方（口令管理带上筛选、代理和成员那一行会高亮、版本直接打开详情）。只搜你有权限看的。

左栏的「当前概览」看的是当前这一个 App。最上面是启动失败告警（有版本启动失败偏多时才有，固定在最上面，不能拖走），下面是一块可以调整的看板，默认从上到下是：待处理和运行模式、「开始使用」（接入、发布、新建口令、下载备份四步没做完时显示）、今天的看板，最下面是版本覆盖和代理排行、最近激活和最近操作；默认布局的每一行是排好的，哪张卡片内容少（比如最近操作只有一条）也不会挪到别的卡片下面。右上角「调整看板」进入调整：每张卡片的标题行换成一条工具条（左边是卡片名，右边是宽度 ¼、⅓、½、⅔、整行和收起 ×），虚线框贴着卡片边；按住卡片拖（卡片浮起来跟着鼠标，原来的位置换成虚线占位框，其他卡片滑开让位置；平板上按住工具条拖），拖卡片右侧的把手或者点工具条上的宽度改宽度，宽度按一行 12 列吸附；拖卡片底边的把手改高度，只改这一张：一个虚线框跟着指针，卡片在这一行能对齐的范围里跟上，旁边的卡片在各自的范围里补齐；每张卡片最矮是内容刚好显示完整（按它当时的宽度算），最高按种类定（数字卡片能拉到两张叠起来那么高，运行模式这类横着排的只能高一点），拉过头有阻力、提示为什么停在这里（自己最高 / 最低，或者旁边的卡片跟不上），松手弹回；拉得比旁边的卡片高出一截时，旁边的卡片叠成一列排在它旁边（一张高的旁边两三张矮的），拉回来又散开，拖的时候就是松手后的样子；双击把手回到自动高度，「高度全部自动」把拉过的高度都去掉（顺序、宽度不变）；点 × 收起，「添加卡片」按常用、激活、口令与代理、发布、设备与系统分组列出全部 33 张，「恢复默认」回到原样；也能用键盘：选中卡片后方向键挪位置、Shift + 左右改宽度、Shift + 上下改高度、Delete 收起，拖到一半按 Esc 放回原处。手机上卡片收成只剩工具条，整块看板变成一张短列表：点 ↑ ↓ 挪一个位置，或者按住左边的把手拖（工具条别处照常上下滑），× 收起；调整条固定在屏幕底部，「完成」随手够得着。一行里可以随意组合，比如一张 ⅔ 配一张 ⅓、一张 ½ 配两张 ¼；同一行的卡片顶边、底边始终对齐，高矮差太多、怎么都对不齐的不排在同一行；每一行在接下来的几张卡片里挑最好的排法（空当少、拉伸少、少叠、拉过的高度尽量不变），高卡片旁边可以叠两三张矮的；排好的样子（哪张开始新的一行、哪张叠在哪张下面）跟着布局一起存，打开、刷新、换设备都原样还原，改哪一行只重新排那一行，别的行不动；拖动、改大小时别的卡片实时滑到新位置，卡片里的内容按卡片自己的宽度排版。看板布局存在账号上，同一浏览器开着的其他标签页马上跟着变，别的设备 30 秒内跟上。默认布局里没权限看的卡片空出来的位置，同一行的其他卡片会匀开占满。除了原来的卡片，还有：计划任务（等着执行的定时切换和定时调灰度按时间列出，带倒数和取消，下面是最近执行的结果；没有计划时可以直接去设）、激活时段（近 4 周按星期和钟点的热力图）、本周对比（这周每天和上周同一天）、激活转化（今天提交和确认的环形图、近 7 天确认率）、今日目标（自己定个数，看完成了多少）、便签（只有自己看得到，停下来自动保存）、热门口令、灰度进度、快到期的口令、口令申请、代理公告、发布记录（时间线）、安装包、设备构成、最近启动错误、快捷操作，超级管理员还有运行状态和登录动态。看板、便签和今日目标存在自己的账号上，每个人可以不一样，没权限的卡片不显示。今天的看板：今日有效激活（比昨天、提交次数、确认率）、按小时的分布和高峰（还没到的钟点只画一条底线）、今天有激活的代理（几个 / 启用中几个）、今天用到的口令、提交了还没确认的、待审核的口令申请。下面三张汇总卡：口令（可用、已用完、已过期、停用的占比，点了直接筛选；7 天内到期的会提醒）、代理（启用中、今天有激活、待审核）、累计有效激活（近 7 天比前 7 天和趋势线）。第二块是设备：今日活跃设备（比昨天）、今天的新设备、近 14 天每天的活跃设备、近 7 / 30 天活跃、近 7 天日均和今天的 iOS 占比；「设备统计」页有近 30 天的日活柱状图（每根柱子按 iOS / Android 分两段，鼠标放上去看数字），版本分布旁边是设备构成：iOS / Android 占比、各渠道和各 Runtime 的设备数。设备每天第一次检查更新时记一次活跃（`ota_device_daily`，留 400 天），今天的数直接按设备表算，升级当天之前的日子没有记录，图上画成斜纹并写明从哪天开始记录。概览和代理后台的概览标着「实时」，页面开着时每 30 秒自动刷新数据（不闪、不跳回顶部；开着弹窗或者正在输入时先不刷）。有效激活趋势可以切 7 / 14 / 30 天，标题旁边是这段时间的合计和比上一段的变化。

## 数据大屏

当前概览右上角「数据大屏」打开，适合投到大屏或者开着放在一边。标题那里点一下（或者按 `/`）切换看哪个 App，也可以选「全部 App」，几十个 App 也能搜。

- **一个 App**：顶上一排关键数字（累计和近 7 天的有效激活、今日活跃和新设备、口令、代理、启动失败），中间是今天的有效激活（比昨天同一时段、按小时的分布），旁边是代理排行和热门口令；下面是近 30 天趋势、设备、版本覆盖、设备构成、各渠道的线上版本和最新动态。
- **全部 App**：同样的关键数字合在一起看，App 排行（今日激活、比昨天同一时段、近 7 天、近 14 天的小趋势线，一屏两列，放不下的合成「其余 N 个 App」一行），上线中、今天有激活的 App 有几个。
- 今日有效激活的圆环：圆点拖着一段柔和的光尾，光尾里几股粗细、快慢不一的颗粒冲向圆点（圆点本身不闪）；刻度里面那一道是「昨天此刻」（昨天到现在这个钟点的激活占昨天全天的多少）。比昨天此刻少时颗粒慢慢流；超过以后颗粒更密更快、往外散得更开，圆点前面还甩出几颗，领先得越多越激烈（多出昨天同一时刻的六成、至少 5 台算满）；每次刷新今天的数涨了，一道光顺着光尾冲进圆点、圆点亮一下；到了昨天全天（昨天没有就按近 7 天日均）满一圈，外圈柔柔地亮一下，之后的进度是贴着圆环的一道亮线接着往前走（满过的圈淡一些），每满一圈亮一下。圆环中间写「已达昨天 N%」（昨天没有时是「已达 7 日均 N%」），两倍以上在下面一行用金色字标 ×N，圆环本身不变色。深色、浅色都用主题色，浅色下是带主题色边的白色圆点、颗粒用主题色。颗粒和圆点各画在一层，颗粒每一帧只重画自己那层，圆环和圆点的光晕不跟着重算，配置低的电脑也流畅；颗粒的亮度和快慢由页面直接算好，不依赖浏览器对 CSS 计算的支持。「今日提交激活」下面的待确认只算今天提交、还没确认的；激活趋势的日均、最高写在标题那一行，曲线上不再另外标最高的数字，最高那天离顶只留一点点空（纵轴最上面是比最大值大一点的整数），鼠标停在哪一天，竖线和圆点正对那天的点。代理排行只列今天有激活的代理，今天没有激活的不拿来补位（一个都没有时写「今天还没有代理激活」）；App 排行里今天没有激活的不标名次。
- 每 10 秒自动取一次数据。数字像里程表一样滚到新值（变大时每一位都往上滚，9 之后接着滚到 0，多出来的一位从空白滚进来，不会倒着数），旁边弹出「+N」，排行名次变了标出 ▲▼ 并滑到新位置，变了的行亮一下；列表不会自己滚动、翻页，只在有新数据时才变。
- 默认深色，右上角可以换成浅色，存在自己的账号上，和后台的深色 / 浅色互不影响；颜色跟着外观里选的主题色。还有全屏按钮。
- 1200 × 700 以上一屏放下、不滚动，每个列表按屏幕高度显示整数行；小一点的屏幕和手机上改成上下滚动。

### 分享数据大屏

右上角「分享」生成一个不用登录就能看的链接（`/s/口令`），打开看到的和分享的人在后台看到的一模一样（一样的数据、外观、每 10 秒自动刷新），只是不能操作：没有切换 App、回后台和分享按钮，待处理只显示不能点，深色 / 浅色只在对方自己的浏览器里换，页脚写着分享到什么时候。

- **新建**：分享当前这个 App 或者全部 App（能看到两个以上 App 时可选）；有效期 1 小时、1 天、7 天、30 天或长期；访问密码可选（4–32 位，打开开关自动生成一个随机的，可以改）；备注只在分享记录里看得到。生成后给链接和二维码，密码只在这时显示一次，可以一键复制「链接 + 密码」。
- **分享记录**：每个分享的状态（有效 / 已过期 / 已取消）、还剩多久、要不要密码、打开过几次和最近一次、谁在什么时候生成的；有效的可以复制链接、打开、取消（点两下确认）。成员只看得到、取消得了自己的，超级管理员能看到、取消所有人的；每人最多同时 50 个有效分享。生成和取消都记在操作日志里。
- **转发**：分享出去的页面右上角也有分享按钮，手机上调系统的分享，电脑上复制这个链接；只是转发同一个链接，不能新建分享。
- **打开**：带密码的先输密码，输对后这个浏览器记住（签过名的 Cookie，最长 30 天、不超过分享的有效期），同一个 IP 10 分钟内输错 8 次先锁住；过期、取消了、分享的人被停用或者看不了那个 App 了，打开显示分享已失效，开着的页面下次刷新就变过去。数据按分享的人现在的权限取，后台页面的脚本和样式凭有效分享的 Cookie 才取得到，进不了后台。
- **App 图标**：分享出去的页面从分享自己的地址取图标（`/s/口令/icon/App ID`），不用登录也显示；只给分享范围里、分享的人现在还看得到的 App，带密码的要先输对密码，分享失效了就取不到。
- 演示环境不能分享。

## 新版本提示

后台和代理后台开着时每 10 秒问一次服务端的版本号（`/app/version`，只返回版本号，低优先级的后台请求；后台页每 30 秒顺便用 `/admin/pulse` 更新待处理；页面在后台或断网时不问；切页时页面数据的 `X-OTA-Build` 响应头也带着）。概览这类「实时」页面每 30 秒取一次数据，数据没变就不重画页面，看不出任何动静。替换 jar 重启以后，已经打开的页面会弹窗「后台已经更新」，显示新版本号和发布时间，按回车或点「重新加载」换成新页面；页面上有没保存的输入时会提醒先保存。点「稍后再说」右下角留一个小提示条，随时点。手机上是从底部弹出。版本号由前端文件和打包时间算出来，不用配置。

## 中英文切换

顶栏搜索框右边的「🌐 EN / 中」一点就切换（代理后台顶栏、登录页右上角也有；手机上顶栏只显示地球图标；外观菜单里也能选），只对自己的浏览器生效。选 English 时页面上的文字、提示、按钮、标题在显示前换成英文（`frontend-vue/src/i18n`），中文用户不加载词典。每句话只查一次（缓存），词组用前缀树一遍扫完，切页、自动刷新时几乎不占时间；English 模式会关掉浏览器自带的网页翻译（Safari、Chrome、模拟器里的「翻译此页」），免得两边来回改把页面卡住，万一还有别的脚本反复改同一段字，改几次之后就不再跟着翻。代理名字、备注、版本说明这些数据保持原样；操作日志的详情按固定句式翻成英文，里面的名字、标题、备注保持原样。改了页面文字后运行 `node tools/i18n-extract.mjs` 列出还没翻译的句子，加进 `src/i18n/en.js`。

## 外观和品牌

「系统配置 → 外观」（超级管理员）：

- **后台名称**：显示在侧栏、登录页和浏览器标签上，最多 20 个字。
- **登录页标语**：登录页左边的大标题（最多 30 个字）和一句说明（最多 60 个字），比如公司名、口号，留空用默认。
- **一键风格**：12 套，一行三套：通用的（默认、清爽、极简）、稳重的（商务、科技、沉稳）、明快的（活力、暖阳、甜美）、有个性的（自然、典雅、莫兰迪）。点一下把下面几项一起选好，还能再单独改。
- **主题色**：24 种，按钮、选中态、图表都跟着变。一行一个色系，顺着色环排：鲜明的冷色（靛蓝、经典蓝、天空蓝、青碧、翡翠绿、橄榄绿）、鲜明的暖色（琥珀、活力橙、中国红、玫瑰粉、品红、紫罗兰）、浓郁的深色（午夜蓝、墨青、墨绿、咖啡棕、酒红、暮紫）、柔和的莫兰迪色和中性色（雾霾蓝、灰豆绿、燕麦、豆沙粉、石板灰、经典黑白）。每个颜色上的白字、当文字用时在白底上都看得清，深色模式自动换成同色系亮一档的；任意两个颜色并排都分得开。以前选过胭脂红、翡翠、葡萄紫、石墨的，自动换成最接近的中国红、墨绿、紫罗兰、石板灰。
- **圆角**：直角到圆润五档。
- **侧栏**：主题色（默认，按主题色算出深一档的渐变）、深色、浅色。每个人还能在右上角的外观菜单里给自己换，存在自己的账号上；菜单里标着「默认」的就是系统配置，选它就跟着系统走。在这里保存外观时，自己浏览器上的侧栏选择会清掉，马上看到保存的效果。主题色选经典黑白时，主题色侧栏也是黑色。代理后台的顶栏和登录页左侧也用主题色。
- **页面宽度**：宽（默认，内容最宽 1560 像素）、标准（1240 像素，两边留白多）、铺满。
- **卡片**：轻阴影（默认）、描边（只有细边框）、浮起（没有边框、阴影更立体）。
- **页面背景**：浅灰（默认）、纯白、点阵、光晕（顶部一层淡淡的主题色）。深色模式下纯白和浅灰都用深色底。
- **按钮**：立体（默认）、扁平、发光（渐变加主题色的光）。
- **表格**：分隔线（默认）、斑马纹。

选了马上能在整个设置页上看到效果，保存后所有人生效（代理后台和登录页也一样）；没保存就离开会先问一句。每个人的深色模式、信息密度在外观菜单里选。

「App 设置 → 基本设置」可以上传 App 图标（PNG、JPG、WebP，最大 512 KB，建议 512×512），侧栏切换器、所有 App、代理后台都会显示；图标也在 App 备份里。「App 设置 → 口令接口」除了 App Key、签名密钥和请求头格式，还有「在 App 里调用」：兑换、校验、确认三个接口各在什么时候调，以及一段填好了这个 App 的 Key 和地址、可以直接复制的签名请求示例。

## 计划任务

- **定时切换 A/B 面**：概览「运行模式」卡片右上角「定时切换」，选 A 或 B 和时间。比如审核通过后约好时间上线。
- **定时调整灰度**：「版本发布」里每个渠道灰度旁边的日历按钮，选比例和时间。到时间如果这个渠道的线上版本已经换了，就不执行（免得把新版本直接放量）。

最多提前 90 天，按后台时区。到时间自动执行（每 30 秒检查一次），照常记操作日志（操作人「计划任务」）、发通知；「版本发布」页能看到等执行的和最近 7 天执行过的（已执行 / 没执行），等执行的可以取消；取消的计划不再显示在页面上，只在操作日志里留一条「取消计划」。定时切换要「切换 A/B 面」权限，定时调灰度要「发布版本」权限。CI 也可以用管理接口 `/api/v1/apps/{app}/schedules` 或 `ota schedule` 设（定时调灰度可以用发布令牌，定时切换要管理令牌）。

## 版本发布页

分三个标签：**渠道和版本**（默认）、**发布记录**（最近 10 条）、**安装包**。

- **线上版本**：每个渠道一行，列是渠道（和 Runtime）、线上版本（和上一版本）、灰度（分两段的条，写明其余设备用哪个版本，没有上一版本时「其余先不更新」）、设备（装上 / 推送、装上率、启动失败）、最近操作（时间和操作人）。每行只露出「调整灰度」「回滚」两个按钮：调整灰度在弹窗里填比例或点 10% / 30% / 50% / 100%，下面的条跟着变，也能改成定时调整；「⋯」菜单里是定时调整灰度、推到其他渠道、回退内置版本。线上版本那一格标着「常规更新」，每行下面是一条「口令更新」：设了口令更新包时显示版本和说明，可以更换、取消；没设时写着「跟常规更新一样」，点「单独设置」，见「常规更新和口令更新」。最近操作取常规更新和口令更新包里后改的那个。更新地址在标题栏右边，点一下复制。卡片宽度不够时每行折成两行，手机上竖排。
- 渠道回退到安装包内置版本后，那一行标出「安装包内置版本」、回退时间和回退前的版本，按钮只有「恢复到一个版本」。
- **版本列表**按 Runtime 分组，列是版本（版本号和说明，回滚时复制出来的标「某某的副本」）、渠道（在哪个渠道线上 / 是哪个渠道的上一版本 / 是哪个渠道的口令更新包）、设备、发布时间（下面是发布人和大小）。每行只露出「发布」（弹窗里选发布成常规更新还是口令更新），详情、校验、删除在「⋯」菜单里；不能删的版本菜单里写明原因，见「版本回滚」里的删除规则。
- 「安装包」标签上面是上传区，下面每个安装包一张卡片：平台、版本号、包名和结论，四项检查（更新地址、运行版本、渠道、签名）分成小格，底部是文件、Runtime、备注和上传人。

## 备份与恢复

后台「App 设置 → 备份与恢复」可以下载一个 App 的备份：签名私钥和证书、口令接口的 App Key 和密钥、授权签名密钥、Webhook、渠道和全部口令。口令所有 App 通用，每个 App 的备份里都是全部口令，恢复时只补上缺的。备份用你设的备份密码加密（PBKDF2 + AES-256-GCM），下载和恢复都要先输自己的登录密码。备份里还有测试设备和群机器人地址。

- 服务器或数据库丢了：在新服务器的「所有 App → 从备份恢复」里恢复，App、密钥、口令都和原来一样，已安装的 App 和用户手上的授权继续可用。
- 密钥被误换：在原服务器上勾选「覆盖」恢复，改回备份时的密钥。

版本文件和激活记录不在 App 备份里，版本可以重新发布。

### 项目备份（整个后台）

「系统配置 → 备份」（超级管理员）：

- **下载完整备份**：数据库（所有 App、版本记录、口令、激活记录、代理、成员、设置）、版本文件和图标、签名私钥、主密钥、安装配置打成一个 `.otaproj` 文件，用你设的备份密码加密（PBKDF2 + AES-256-CTR + HMAC）。下载前要输自己的登录密码；服务器先把备份完整写到数据目录的 `tmp/downloads`（按钮上显示进度），写完才开始下载，按实际大小传，打包出错会直接提示，不会下到半截文件；下载完或一小时后临时文件自动删除。页面上的「压缩前大小」只算会放进备份的内容（数据库文件、本机存储的文件），打包时会压缩，下载的文件一般小一些。数据库是 MySQL 时请另外用 mysqldump 备份；文件存在 S3 时不放进备份。
- **自动备份**：每天固定时间在服务器上存一份（数据目录的 `backups` 下，不加密，和数据目录一样敏感），保留最近 N 份。也可以点「现在备份一次」。列表里的每一份都能下载（下载时加密）、恢复、删除；把下载的 `.otaproj` 放进 `backups` 也会出现在列表里。想在别的机器上也留一份，可以用 rsync 之类定时同步 `backups` 目录（里面有签名私钥和主密钥，同步到的地方要同样保密）。完整备份只能在后台输登录密码下载，管理接口不提供，免得令牌泄露时私钥被拿走。
- **恢复**：上传 `.otaproj`（分片上传，不受反向代理大小限制）或者选服务器上的一份，输备份密码和自己的登录密码。检查通过后服务在进程里自动重启，打开数据库之前把数据换成备份里的（`RestoreOnStart`），所有人要重新登录。原来的数据挪到数据目录的 `restore/before-时间` 下（留最近两份），恢复失败会自动换回去。
  - 解密、检查备份在后台做，页面轮询结果，大备份不会因为反向代理等不及（宝塔默认 60 秒）而报错；上传时一片太大（413、宝塔「Nginx缓冲区溢出」）自动减半，断网、一分钟没进展会重传那一片，可以随时取消。等重启的页面显示等了多久，备份有几个 GB 时启动前解压要几分钟。
  - 用了宝塔 WAF 时，把 `/admin/settings/backup/restore` 加进 WAF 的 URL 白名单（恢复 App 备份是 `/admin/apps/restore`），不然加密的备份内容可能被当成攻击拦掉，页面会提示被拦截。

## 删除 App、清理存储

「App 设置 → 删除 App」（只有超级管理员）要输入 App 标识和自己的登录密码，会一起删除它的版本、渠道、这个 App 的激活记录、发布令牌、设备统计、测试设备、版本统计和启动错误，成员对它的授权也一起移除；口令所有 App 通用，不删，代理账号和操作日志也保留。删除前建议先下载备份。管理接口是 `DELETE /api/v1/apps/{app}?confirm={app}`。

版本文件按内容共用，删版本、删 App 时不会立刻删文件。「系统配置 → 存储」显示用量，「清理无用文件」删除 24 小时前登记、没有任何版本在用的文件和用不上的补丁；对象存储里的文件也会一起删掉。

## 切换文件存储

「系统配置 → 存储 → 切换存储」选本机存储或 S3 兼容对象存储，填好后先点「测试连接」（写一个测试文件、读回来、不带签名从下载地址下载一次、再删掉）。App 是直接从对象存储或 CDN 下载文件的，存储桶不是公共读、CDN 没配好时测试不通过，也不让切换，免得切过去所有设备都下载失败。

服务地址填地域节点，不要带存储桶名（阿里云 OSS 如 `https://oss-cn-hangzhou.aliyuncs.com`，腾讯云 COS 如 `https://cos.ap-guangzhou.myqcloud.com`）；误填了「存储桶域名」会自动去掉前面的存储桶名，服务地址是 IP 时自动按路径风格访问。区域一般不用填（AWS S3 要填存储桶所在区域，填错时测试结果会提示应该填哪个）。密钥不对、存储桶不存在、没有权限、连不上等都会直接说明原因。开始切换后：

1. 把所有版本文件、启动包补丁和安装包复制到新存储，每个文件先下载到临时目录核对 SHA-256，对得上才写进去；新存储里已经有的跳过，中途失败可以重新开始，接着复制。
2. 复制完立即改用新存储，再补一遍切换期间新上传的文件，然后写进 `install.json`，重启后保持。
3. 页面上显示进度；结果记在操作日志「切换文件存储」里。原来存储里的文件不会删除，确认没问题后可以自己清理。

原来的存储连不上（存储桶删了、密钥失效、服务停了）时没法复制，开始切换后先检查新存储里已经有哪些文件：

- 版本和安装包的文件新存储里都有（比如同一个存储桶换了密钥），直接换过去，什么都不删。
- 有缺文件的，弹窗说明原因和会清空什么：新存储里缺文件的版本和安装包（全缺时就是「所有版本」）；文件齐全的版本、外部链接版本留着。确认后清空它们再换过去，渠道上被清空的版本不再下发，设备收到「没有更新」，继续用手机上已经下载的，重新上传同样的包就能补回来。取消就还用原来的存储；只是密钥、权限或网络的问题，修好后再切换，版本都能保留。

文件存储写在启动参数或环境变量里（`--ota.storage.type` 等）时，以启动参数为准，后台不能切换。

## 安装包校验和更新包结构

**安装包（可选）**：「版本发布 → 安装包」上传打好的 APK 或 IPA（最大 1 GB），也可以用命令行 `ota installer upload` 或管理接口传。文件分成几 MB 一片上传，反向代理限制了请求大小（宝塔的 Nginx 默认 50MB）也能传大的 IPA。服务端读出包名、版本号、Runtime、更新地址、请求头里的渠道、内置的签名证书和内置的更新包，逐项检查：

- 更新地址是不是指向这个平台（对外地址或绑定的接口域名）；
- Runtime 有没有已发布的版本，渠道（没写默认 production）在不在、有没有版本；
- 内置证书和这个 App 的签名证书是不是同一把密钥，keyid 对不对（安装包没写 keyid 时 expo-updates 按 `root` 算）、签名算法是不是 rsa-v1_5-sha256；更新开关有没有关掉；
- 渠道上的线上版本是不是比安装包内置版本的打包时间（`app.manifest` 的 `commitTime`）晚：expo-updates 只装比正在运行的版本新的更新，不晚的话 App 会认为没有新更新（提示「更新还没有准备好」），要在打完安装包之后再发布一次；渠道设了口令更新包时比对的是口令更新包（新装的设备拿的是它）；
- 启动时检查更新的时机，读安装包里实际的值（iOS `Expo.plist` 的 `EXUpdatesCheckOnLaunch`，Android 的 `EXPO_UPDATES_CHECK_ON_LAUNCH`）：`ERROR_RECOVERY_ONLY` / `NEVER` 时平时只能靠 App 里调用 `fetchUpdateAsync`；
- 更新地址是不是 HTTPS：明文 HTTP 会被 iOS ATS / Android 拦掉，除非安装包允许明文流量（HTTPS 用非 443 端口没关系，证书受信任就行）；
- 有没有内置更新（回退内置版本要靠它）。

读法改进后，之前上传的安装包在下次查看检查结果时会自动从存着的文件重新读一遍，不用重新上传。

用了宝塔 WAF 时，分片里的二进制内容可能被当成攻击拦掉（返回「网站防火墙」页面，命令行和后台会提示被拦截），把 `/api/v1/apps/*/installers/uploads` 和 `/admin/installers/upload` 加进 WAF 的 URL 白名单。

结果显示在安装包列表里，版本的「校验」也会把同 Runtime、同平台的安装包一起检查。安装包文件存在文件存储里，可以下载；删除时文件没有别处在用才会删掉。

**更新包结构**：版本详情里的「更新包结构」列出这个版本每个平台的全部文件（启动包和资源文件，外部链接版本也能看）、大小和 SHA-256。选一个旧版本对比，每个文件标出新增、有变化、没变或换了位置，以及从旧版本更新过来要下载多少；有增量补丁的启动包在「更新时下载」一栏显示「补丁 大小」，摘要里写明用补丁省下多少流量。

## 代理和口令申请

代理是所有 App 共用的账号，口令也是所有 App 通用的，在「代理管理」里管。每个代理在「编辑」里设置：

- **申请口令**：不能申请（只用分配的口令）、需要审核（提交后等你同意）、自动通过（提交后马上生成）。
- **每天最多申请多少个**：待审核和已通过的都算，自动通过也受它限制；留空表示不限。

代理在代理后台「申请口令」里选方式：**随机生成**（填个数，口令随机 8 位数字）或**自定义口令**（填自己想要的口令，一行一个，比如 88888、VIP2026）；每个口令能激活几次默认 0（不限）。自定义的口令里，已经有的、和别人正在审核的申请重复的，提交时自动拒绝并告诉代理是哪几个。「代理管理 → 口令申请」集中审核：随机申请同意时可以改个数、次数和有效期；自定义申请可以逐个勾选同意哪些口令，没勾的拒绝，生成前会再查一遍、已经有了的跳过；口令随机 8 位数字、直接归属这个代理，备注「代理申请 #编号」；拒绝可以写原因，代理能看到。可以勾选多条批量同意或拒绝；侧栏「代理管理」上的数字是待审核的条数。同意申请要有「口令与激活」权限。

代理在代理后台点右上角自己的名字进「我的账号」，可以改密码（要输当前密码，连续输错 5 次暂停 15 分钟；改好后其他设备上的登录退出）。能看明细的代理可以在「激活记录」里按筛选导出 CSV，扣量、统计截止时间和页面一致，设备号和 IP 脱敏。

「代理管理」上面是合计：代理数、今日有效激活（比昨天）、近 7 天（比前 7 天）、待审核申请和代理手里的口令。代理用卡片显示：今日、近 7 天、累计、可用口令、近 14 天的小柱状图、数据方式和申请方式、扣量、最近登录；可以搜索、按启用 / 停用 / 今天有激活筛选、按今日激活 / 近 7 天 / 累计 / 最近登录 / 创建时间 / 名称排序，也可以切成列表（排序和视图记在浏览器里）。卡片最后是虚线的「新建代理」；「⋯」里可以复制登录信息（登录地址和账号）、导出 TA 的激活记录（所有 App、真实数据，不扣量）；右上角「导出 CSV」导出全部代理和他们的口令、激活数。点卡片进**代理详情**（右上角也能导出激活记录）：今日、近 7 天、累计和代理端看到的数，近 30 天的有效激活图，最近 6 个月按月的提交和有效激活，口令用在了哪些 App（每个 App 的有效激活和占比），激活最多的口令，最近的激活（设备号脱敏），口令申请，TA 自己的操作记录。

代理后台在手机上：口令列表和激活记录排成紧凑的两行（口令、状态在第一行，用量或时间、设备、IP 在第二行），一屏能看更多；其他页面上下排开，不用左右滑。

**公告**：「代理管理 → 公告」发公告，选「全部代理（含二级代理）」或「只发一级代理」，可以置顶，「重要」的会在代理后台概览顶部显示横幅。代理后台多了「公告」页，打开就算看过；后台能看到每条有多少代理看过。开了二级代理的代理在「公告 → 发给二级代理」给自己的二级代理发公告（重要、置顶、已读人数和管理员的一样，只有 TA 自己的二级代理看得到）；二级代理的「公告」里是管理员发给全部代理的和上级发的，上级发的标着「上级代理」。

**扣量**：每个代理在「编辑」里设档位（当天有效激活从几到几扣百分之几，「到」不填表示不限）。每天单独算：当天的有效激活落在哪个档位就按那档的比例扣；扣的条数按各个二级代理（一级代理自己留着没分出去的口令算一份）当天的激活数按比例分摊，再按比例分到每个口令，每个口令扣最晚确认的那几条，所以每个二级代理被扣的比例都一样，除不尽的零头给余数大的那份。改了档位只影响改了以后确认的激活：之前确认的还按原来的档位、按改的那一刻当天的总数扣，扣过的不会因为改比例再变；当天改的，当天后面来的按新档位。

**扣量结算**：扣的结果到了代理的结算时间就写进结算表（`agent_settlement`，一个代理一天一行：结算过的激活记录和其中扣掉的），之后不再变，代理后台读到结算过的直接按表显示。实时和每日 0 点的代理每天 0 点结算前一天的（服务每分钟看一次，停机错过了启动时补上），手动更新的代理点「更新」时结算到更新的那一刻，改档位时先按原来的档位结算到改的那一刻；还没结算的（比如实时代理的今天）按上面的规则现算。口令从别处挪过来的老激活，下次结算时按现在的档位算上。从没有结算表的版本升级上来，第一次启动、对外服务之前，按升级前的算法和当时的档位把每个代理（含二级代理）那一刻看到的数原样写进去，升级不会改动任何已经显示过的数（包括以前二级代理之间没平分的），之后来的激活才按上面的规则；这一步只做一次，日志里会写「已按升级前的算法把 TA 们现在看到的数写死」。

**口令次数按代理看到的算**：代理的口令设了「可激活 N 次」时，扣掉的激活不占次数，口令一直能用到代理看到的满 N 次为止（扣 50% 的话实际大约能激活 2N 台），所以代理那边「用了几次 / 已用完 / 可用口令数」和 TA 看到的有效激活总是对得上，看不出扣了量；分给二级代理的口令按二级代理看到的算，不管 TA 的数据更新到哪天，算到现在。代理端页面数据里只有 TA 看到的次数，没有实际次数。每个口令代理看到了几次存在 `activation_code.seen_count`（激活确认、口令换代理、结算、改扣量以后在后台重算那一家的，启动时和每 10 分钟全部重算一次）；兑换时实际次数已经到上限的当场再算一遍。管理员的口令列表里「有效激活」是实际的，下面标着「代理看到 N」，状态和「可用 / 已用完」筛选按代理看到的算。没分给代理、或者这一家从没扣过量的口令和以前一样按实际次数。

**确认太快的不算**：真手机兑换口令以后要先下载 B 面包、再重启切到 B 面，B 面启动了才来确认激活，从兑换到确认至少要好几秒；兑换后不到 2 秒就来确认的判为脚本刷的，这条激活标成「确认太快」，以后怎么确认都不算有效激活，不占口令次数，不进代理数据和日活。App 那边照常回成功、授权照常有效，不让刷的人看出是哪条规则拦的。管理员的激活记录里单独有「确认太快」（不算待确认），鼠标停在上面能看到兑换后隔了多少毫秒，导出和管理接口（`status=fast`）里也有，操作日志的设备事件里记一条「确认太快」；代理（含二级代理）的激活记录里这条显示「无效用户」，能按它筛选、导出，页面数据里只有是不是无效，没有毫秒数，也不说按什么判的。记在 `activation_record.fast_ms`（隔了多少毫秒，正常的为空）。启动参数 `--ota.min-confirm-ms` 可以改这个时间，0 是不判。

**一台手机只算一次（所有 App 加起来，按开关）**：同一个 App 里，一台设备再兑换同一个口令、或者已经用别的口令激活过，都沿用原来那次激活。跨 App 去重按**每个 App 的开关**（「App 设置 → 按设备去重」，默认关，关着就和最早一样各算各的）：开了去重的 App，确认激活时算这台手机的**设备指纹**，别处已经算过一次有效激活的，这条记成「重复」，不算有效激活、不占口令次数，App 照常能用。

- **指纹怎么算**：首选 `/var/mobile` 的创建时间（系统第一次激活那一刻，毫秒）+ 机型，固定算法算成一个值（`CodeService.deviceFp`）。这个值不同开发者账号的 App 读到的都一样，所以同一台手机在不同 App 里算出来一样，跨 App、跨账号认得出。读不到 `/var/mobile` 时，用公网 IP + 机型兜底（弱一些，换了网络就对不上）；都没有就退回按设备号认（只在同一个开发者账号的 App 之间有用）。
- **接口不变、性能**：App 在 `/v1/codes/verify`、`/confirm` 多带两个可选字段 `init`（`/var/mobile` 创建时间，毫秒）和 `model`（机型，比如 iPhone15,2），老 App 不带也照常工作。请求线程只做兑换、确认这些原来就有的事；记日活、把指纹补写到记录上（`setFingerprintIfMissing`）、更新最近活跃都丢到后台线程、按设备每天最多写一次，不拖慢接口。
- **救老用户**：校验时顺带把指纹补写到这条激活记录上，**升级前就激活的老用户**打开一次就补上，之后同一台手机去别的 App 激活才认得出——所以新 App 上线前，这个带指纹的 B 包要尽早发出去。两个 App 都还没确认的，先确认的算。
- **指纹保留**：每个 App 在「App 设置 → 按设备去重 → 指纹保留」里单独选 7 / 30 / 90 天或一直留着（默认 7 天），一台设备这么久没打开 App 就清掉它的指纹，清掉后它再在别的 App 激活会重新算一次。改短了马上清掉超出的，之后每天凌晨再清一次；刚激活、还没记上日活的设备按激活时间算，不会被误清。
- **日活、显示**：日活记在算过的那一条上，同一台手机一天在几个 App 打开只算一次。管理员的激活记录里单独有「重复」和「非正常」（都不算待确认），鼠标停在「重复」上能看到是按指纹、兜底 IP 还是设备号认的，导出、管理接口（`status=dup` / `fast`，`dupOf`、`dupBy` 是 fp / ip / device）和操作日志的设备事件里也有；代理后台也显示「重复」「非正常」（只给是不是，不给毫秒数和指纹）。记在 `activation_record.fingerprint`、`dup_of`、`dup_by`、`last_active`。

> 读 `/var/mobile` 的创建时间做跨 App 设备指纹，是国内广告行业 CAID 那套做法（你 App 里的广告 SDK 本来就在做），违反苹果 App Store 条款，有拒审 / 下架风险；初始化时间精确到毫秒（不是纳秒），极小概率两台手机撞车，撞了第二台会被当成重复少算一台；手机「抹掉所有内容和设置」、整机恢复后指纹会变，那台重新算。上线前请用真机验一次读得出来。

**二级代理**：管理员在代理的「编辑」里打开「能开二级代理」（可以限个数），代理后台多出「二级代理」页：开账号、分口令（口令仍归上级，激活照常算在上级名下）、设 TA 的扣量和数据更新方式（不能比上级的新）、能不能看设备记录（上级能看才能开）、停用、删除，也能以 TA 的视角查看。二级代理看到的是上级看到的里面 TA 的口令，再按 TA 自己的档位扣一遍。页面上可以选统计时间段（近 7 / 14 / 30 / 90 天、本月、上月、自定义），卡片上是这段时间里自己看到的和二级代理看到的，按月结算时选上个月。管理员在代理详情里看得到每个二级代理的实际激活、上级看到的和 TA 看到的。

**代理后台的数据概览**（二级代理的一样）：累计、今日（实时和手动更新的比前一天同一时刻，每日 0 点的比前一天）、近 7 天、本月都和前一段比。有效激活趋势可以看近 7 / 14 / 30 / 90 天、本月、上月或者自定义起止日期（点「自定义」弹出日历：左边快速选本周、上周、本月、上月、近 3 个月、今年、去年，右边并排两个月点开始和结束日期，最长 366 天、最晚到统计截止那天；手机上是底部面板、一个月。超过 92 天按月画柱子），下面是这段时间的合计、日均、最高一天、有激活的天和比前一段；「按月统计」列最近几个月每个月的数；开了二级代理的能看到这段时间里每个二级代理带来的（按自己看到的算，没分出去的口令单列一行），没开的看最新公告；「我的口令」里每个口令多一列这段时间里的数。

**日活与留存**（只有管理员能看，代理后台和二级代理后台都没有）：App 启动时向服务器校验授权（`/v1/codes/verify`）或者确认激活成功，这台设备这一天就算打开过，一天只算一次，算在激活它的口令名下；都是真实的数，不扣量。记在 `activation_day` 表里（一台设备一天一行，保留 400 天，删 App 时一起删）。从装上这个版本那天开始记，之前哪天谁打开过没有记录，补不回来；没联网、或者 App 启动时不向服务器校验的，那天不算。入口：「代理」右上角「日活与留存」看全部代理，代理卡片的菜单和代理详情里看一个代理（含 TA 的二级代理），口令列表里分给代理的口令点「日活」单看这一个。页面上选近 7 / 14 / 30 / 60 / 90 天，看今日日活和今天新激活的、昨日日活比前一天多了还是少了多少、活跃率（昨日日活占累计激活的多少）、次日留存（近 7 天新激活的设备第二天又打开的占多少）、7 日留存；每天的日活柱子分成之前激活的和当天新激活的，旁边是近 7 天日均比前 7 天；「新激活的留存」表列每天新激活了几台、之后第 1 / 3 / 7 / 14 / 30 天又打开的占多少（还没到那天的显示「…」）；下面按代理、按二级代理（没分出去的口令单列一行）、按口令列出累计激活、今日、昨日、比前一天和次日 / 7 日留存，点名字进去看那一个。

**7 日留存（代理后台也能看，结算方便）**：代理后台多一个「留存」页（二级代理也有），管理员在代理详情、日活与留存页点「7 日留存」看某个代理的。选时间段（近 7 / 14 / 30 天、本月、上月、自定义日期），顶上两张卡是这段时间加起来的次日留存和 7 日留存，下面按天列出每个激活日第 1 到 7 天的留存（封顶 7 天，颜色越深越高，第一行是合计）。代理那边只给百分比、不给台数（不泄露扣量前的真实数），手机上卡片竖排、表格横向滚动。

多个代理一起改：在「代理」里勾选，批量设置申请方式、启用、停用或删除。删除代理时选「只删账号」，TA 名下的口令改为未分配；选「连口令和激活记录一起删」，TA 名下的口令、这些口令的激活记录和申请一起删除，要输入自己的登录密码。

## 后台前端

后台是 Vue 3 写的。浏览器直接打开页面（地址栏、刷新、查看源代码）时服务端只返回加载壳，页面数据由脚本取回后渲染，「查看源代码」看不到页面内容；后台页面的脚本和样式只发给登录了的人。服务端只把页面上显示的字段发给浏览器，密码、密钥这类字段不会发送，没有「App 设置」权限的人拿不到 Webhook、群机器人地址和口令接口密钥。

页面上的小细节：

- 往下翻得多了，右下角出现「回到顶部」。
- 弹窗打开时光标直接在第一个输入框里（手机上不自动弹键盘）。
- 鼠标停在数字框上滚动页面，不会顺手把数字改了。
- 搜索框里按 Esc 清空；已经按关键字搜过的，清空后马上重新列出全部。
- 表单改了没保存就点别的页面，先问一句「有改动还没保存」；关浏览器标签、刷新时浏览器也会提醒。
- 断网时页面顶上提示一条，恢复后自动收起。
- 所有密码框在大写锁定打开时提示一句；登录页勾了「记住我」会记住上次的账号，下次直接输密码。
- 激活记录里的设备 ID 能点，点了只看这台设备的激活。
- 手机上顶栏只留菜单、搜索、语言、深浅色、待处理和帮助，不显示演示环境和 A/B 面标记。
- 左右并排的卡片（概览、设备统计、我的账号、代理的申请口令页）一样高。

## 升级

以前用过 `--ota.ui=vue` 的，这个参数已经不需要了（带着也没关系）。

**先停止服务，再替换 jar，再启动**（或者把新 jar 上传成别的文件名，用 `mv` 覆盖后重启）。不要在服务运行时直接覆盖正在运行的 jar：运行中的程序会因为读不到原来的类而出错。万一覆盖了，程序会发现并马上把数据写入磁盘、在日志里提示，重启后数据完整。

数据库表和字段自动补齐（新增 `ota_admin_user`、`ota_admin_grant`、`ota_login_record` 等）。从没有安装引导的旧版本升级时，第一次启动会按现有数据自动记为已安装、写好 `install.json`（沿用原来的启动参数），不会出现安装页面；原来的后台账号自动成为超级管理员，账号密码不变。版本统计从升级后开始累计。

### 项目结构

服务端（`src/main/java/com/ota/platform`），按业务分包：

| 包 | 管什么 |
| --- | --- |
| `manifest`、`patch` | 给 App 用的接口：检查更新、增量补丁 |
| `release`、`pkg`、`installer` | 版本和发布、更新包导入和校验、安装包解析 |
| `ota`、`stats`、`webhook` | 设备统计、启动失败、模拟检查更新、事件通知和发送记录（`NotifyDeliveries`） |
| `codes` | 口令、激活记录、口令兑换接口 |
| `agent`、`notice` | 代理账号、口令申请和审核；代理公告和已读 |
| `app`、`signing`、`backup` | App 和渠道、App 图标（`AppIcons`）、签名密钥；App 备份（`BackupService`）和项目备份（`ProjectBackupService`、`RestoreOnStart`） |
| `schedule` | 计划任务：定时切换 A/B 面、定时调整灰度 |
| `demo` | 演示账号：独立的演示环境（`DemoSandbox`）、请求转发（`DemoProxyFilter`）、演示环境里的限制（`DemoGuard`） |
| `admin`、`security`、`auth` | 管理员和权限、登录和两步验证、API 令牌 |
| `settings`、`storage`、`install` | 系统配置（主题色、侧栏、圆角、后台名称在 `ThemeCatalog` / `SettingService`）、文件存储、安装引导 |
| `api` | 管理接口（命令行和 CI 用），计划任务接口（`ScheduleApiController`） |
| `web.admin` | 后台的页面控制器、待处理汇总（`TodoService`）、⌘K 数据搜索（`AdminSearchController`）、铃铛和版本号轮询（`AdminPulseController`）、项目备份（`AdminBackupController`）、计划任务（`AdminScheduleController`） |
| `web.agent` | 代理后台（`AgentController`、`AgentPortal`） |
| `web` | 后台和代理后台共用的：显示格式（`AdminUi`）、主题和后台名称（`ThemeAdvice`）、CSV 导出、首页和健康检查 |
| `web.page` | 页面怎么送到浏览器：加载壳（`VueUi`）、页面数据（`PageData`）、跳转带标签（`RedirectHash`）、错误页套主题（`ThemedErrorViews`）、版本号（`BuildStamp`、`/app/version`） |
| `audit`、`common`、`config` | 操作日志、公共工具、Spring 配置 |

后台前端（`frontend-vue`，Vue 3 + Vite）：

- `src/views`：页面组件（`pages/` 是页面，`frags/` 是公共部分），表达式按 Java 的规则求值（`src/runtime`），显示出来的数字、日期和服务端一个字符都不差。
- `src/behaviors`：页面上的交互。`ui.js` 管弹窗、引导、标签栏、搜索和动效，`pages/` 是各页面自己的脚本；`src/main.js` 取页面数据、切页、提交表单、前进后退。
- `src/css`：样式。登录页、安装页、错误页用的打包到 `static/vue/assets`（公开），后台页面的打包到 `static/vue/app`（要登录）。
- `src/i18n`：英文词典和切换（`en.js` 只在选了 English 时加载）。
- `cli`：命令行工具 `ota`（发布、安装包上传）。
- `deploy`：生产配置示例、`docker/`（Dockerfile 和 docker-compose）、`sql/`（要手动执行的数据库调整）。
- `tests`：全量回归和测试工具；`scripts`：新电脑装开发环境。
- `src/main/resources/demo/seed.zip`：演示环境的默认数据。

控制器照常返回页面名和模型，`PageData` 把页面用到的字段转成 JSON 发给浏览器。用到哪些字段写在 `src/main/resources/vue-fields.json`，`npm run build` 时从组件里统计出来（`tools/fields.mjs`），组件里用到新字段时重新打包就行。页面里没有内联脚本，响应头带 CSP，只允许加载本站脚本。打包结果提交在仓库里，只改了 Java 时直接 `mvn package` 也行。

`npm run build:ssr` 打一个服务端渲染包，`npm run ssr` 启动渲染服务，测试用它把页面数据渲染成 HTML 再检查；它不进 jar。
